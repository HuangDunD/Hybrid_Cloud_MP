## 1. 两条主线及其交汇点

**可见性主线回答“这笔事务能看哪个版本”；undo 主线回答“这个版本在哪里，如何保留、重建和回滚”。** 先分别验证基础能力，再把它们接入真实读写路径。只有 SCN 比较、没有历史读取，不能称为完成 MVCC；只有旧值链、没有安全的快照发布，也不能保证快照一致。

| 主线 | 任务 | 交付内容 |
|---|---|---|
| V：可见性 | V1 身份与快照；V2 提交发布；V3 可见性与写冲突；V4 多参与者统一终态；V5 快照保留与状态保留 | 固定 snapshot_scn，正确的 commit_scn 和事务状态，安全的新快照边界，所有读写入口使用同一语义 |
| U：undo 引擎 | U1 页与段；U2 缓冲池及页权限；U3 redo 与回放；U4 挂链、历史读和逆序回滚；U5 GC 与复用 | 可以跨节点定位和读取的完整旧行，独立缓存，经已有 WAL 重建页面，安全回收 |

推荐执行顺序如下。P1、P2 在 P0 的约定稳定后具有一定独立性，但涉及共享行格式、页身份和 WAL 字段时应按同一版本实施，默认串行完成。

| 阶段 | 主线 | 范围 | 退出条件 |
|---|---|---|---|
| P0 | V + U | 补齐 SCN 协议和共享约定 | 状态、时序、字段职责和读写入口清单明确，并解释并发反例 |
| P1 | V | SCN、事务状态与可见性基础 | 受控并发测试证明快照不会倒退或事后纳入提交；暂不声称真实数据已支持 MVCC |
| P2 | U | undo 页、段、独立缓存、redo / replay | 页可追加、跨页读取、淘汰后重建，重复回放正确；暂不复用历史空间 |
| P3 | V + U | 单节点 Lazy 闭环 | 真实行的历史读、自读、写冲突、回滚、删除标记均正确 |
| P4 | V + U | 多节点 Lazy 与页面迁移 | 新快照包含已成功提交，跨节点历史读、页迁移和淘汰正确 |
| P5 | V + U | 2PC、mix 及现有变体 | 所有参与者统一可见，覆盖 Prepare / Commit 和零、单、多写参与者路径 |
| P6（延期） | U + V | 可选 GC、事务状态回收与页复用 | 当前不实施；启用回收前再按本节验证安全性 |
| P7（P5 后直接进行） | V + U | 负载正确性验收与性能记录 | 三类负载、三类模式及相关分支通过，记录成本和已知限制；不要求 GC |

**P7 当前范围已完成，P6 的 GC/历史截断/状态回收/页复用按 2026-11-19 调整延期，不自动扩展。** 先核对工作区和实施进度顶部；P7 的矩阵、命令、性能和未验证项见 [P7 验收报告](UNDO_MVCC_P7_ACCEPTANCE.md)。阶段内部常规选择自行处理，范围变更以用户当前要求为准。

## 2. 必须延续的已确认选择

1. 事务级 SI。Begin 固定 snapshot_scn；自身写入优先；其他版本只有在创建事务全局 COMMITTED 且 `commit_scn <= snapshot_scn` 时可见。初始化版本有明确规则；遇到可见墓碑立即返回不存在。写者取得写权限后，还要检查是否存在比本快照更新的已提交版本，有则回滚重试。
2. tx_id、snapshot_scn、commit_scn、WAL LSN 各司其职。普通 ID 可以批量分配；当前批量时间戳不能直接成为可见性顺序。Begin 的目标是取得本地维护的有效快照边界，提交承担必要的集群同步等待。
3. Begin 建逻辑 undo 段，首次写才分配物理页；2PC 各实际写节点管理子段并使用自己的 WAL。每次实际覆盖保存完整逻辑旧行，包含版本创建者、删除状态、前一 undo 引用；不复制锁、等待队列或进程指针，首版不合并重复覆盖。
4. Lazy 保留执行阶段覆盖共享行的方式，先保存 undo 再覆盖；2PC 保留私有执行、Prepare 准备旧值及 undo、Commit 安装新行的方式。单写参与者捷径不强加 Prepare。整笔事务发布前，不能让下一写者取得其行写权限。
5. undo 使用 4 KiB 页；每个计算节点设置独立、共享于所有事务的 `undo_buffer_pool_size_pages`，初始 10,000 页。复用现有页权限和缓存机制，允许增加历史访问带来的页面迁移成本。
6. undo redo 与实际写节点的现有 WAL 共流，由存储端回放写页。不另建计算端脏页落盘机制；保留现有批量刷新策略和必要等待点，不对每条 undo 单独同步刷盘。实际刷新次数可能随日志量、页面访问变化。
7. Lazy、2PC、mix 全覆盖。只覆盖 YCSB、SmallBank、TPC-C 当前真实操作，包括旧写回路径和删除标记；不新增 SQL MVCC、通用 INSERT / DELETE、改主键或范围查询。
8. 保护长快照，空间压力限制新写入，保留回滚资源。不做自动过期快照、不静默丢历史。保留并检查必要 WAL/页级 redo 机制；正常运行、页面重建和重复应用的组件正确性与完整故障恢复验收分开，不扩展断线重试、事务崩溃决议、接管或 HA。当前磁盘配额与 GC 尚未实现，不能把这些要求当成已有能力。

## 3. P0：协议与共享约定

本阶段先解决“什么才算可以发布的提交”，随后才能写有意义的可见性代码。已确认 SCN 路线，不重新讨论是否采用活跃事务集合过滤。

### 任务

- 列出现有 Begin、只读、读后写、回调更新、旧私有副本写回、Commit、Abort、远端取页、Prepare、延迟清锁的入口，按 Lazy / 2PC / mix 对照，标出实际覆盖主行的位置。
- 明确事务身份及运行代次、snapshot_scn、commit_scn、初始版本、版本创建者、undo 引用、日志流身份与 LSN 的职责。版本创建者与当前锁持有者必须分开。
- 定稿正常运行时 SCN 协议：谁分配提交位置；怎样处理同时提交和空洞；持久化、写项安装、事务终态、广播 ACK、快照边界推进分别发生在哪里；Begin 与发布的先后关系如何确定。
- 首版优先采用容易证明正确的统一提交编号/发布协调方式，允许提交侧存在中心协调点；Begin 仍取本地有效边界。具体算法由本阶段写清，不以独立的本地 `max + 1` 加广播代替协议，也不预设一定比逐事务取号更快。
- 明确 RPC 参与节点集合和 ACK 含义、合法重复请求的处理、全局提交状态从哪里读取和缓存。已决定提交后的消息延迟不能被解释成可随意 Abort；本轮不新增故障决议协议。
- 明确快照登记与未来 GC 的约定：快照开始使用前已受保护；远端参与者使用同一快照；全局保留水位不得越过尚未报告但已开始使用的快照。
- 明确 undo 页身份、段/子段身份、稳定引用与代次、行链和事务回滚顺序、页内记录完成后才能发布引用的约定。规定持页 latch、获取页权限、等待 WAL / RPC 的锁顺序，避免持住主行页等待 undo 页造成循环等待。
- 列出需改动的行序列化、加载器、页容量计算、RPC、WAL 编解码及测试布局断言。不要照抄当前 `DataItem` 的整结构内存序列化作为逻辑 undo 格式。

### 协议必须解释的时序

| 场景 | 正确结果 |
|---|---|
| A 已取得提交位置 11，但尚未完成；B 的位置 12 已就绪 | 不能只收到 12 就给新读事务快照 12，随后让 A 成为它新出现的可见版本；说明阻塞、排序或其他安全处理 |
| 事务 R 已拿到快照 10，随后 W 提交 | R 的可见集合不会因广播改变；W 不能晚发布为 R 原来缺失、现在突然可见的提交 |
| W 成功返回后，另一节点立即 Begin | 新快照包含 W；此前旧快照不变 |
| 两个节点同时提交，ACK、安装完成、WAL 完成乱序到达 | 不提前成功、不发布半笔事务、不把一次 ACK 算成两个节点 |
| 有提交位置的事务在允许 Abort 的阶段退出，或只读事务结束 | 不留下无法解释的永久空洞；只读结束不必新增提交位置 |
| Begin 与 GC 水位采集并发 | 不能先回收历史，再登记一个仍要使用该历史的快照 |

### 交付与退出条件

新增 `doc/SCN_MVCC_PROTOCOL.md`，包含协议状态转换、消息顺序、并发时序解释及共享字段约定。允许用少量类型和协议测试骨架辅助说明，但不能把未经验证的边界推进接入真实事务。该文档是实现技术细化，不更改 D1—D9。

## 4. P1：可见性基础

### 任务

- 实现 P0 确定的事务身份、固定快照、提交编号/发布、事务状态查询、快照登记与解除。明确只读、运行中、准备中、安装中、全局提交、回滚及终态转换；状态名称可适配项目，不强制引入一套庞大框架。
- 实现候选版本的统一可见性判断和写冲突判断，覆盖自己、初始化、已提交、未提交、已回滚、墓碑和需继续沿链的情况。状态解析失败不能默认为已提交或旧版本。
- 远端执行上下文和各参与者共享事务身份与 snapshot_scn；不得各自重新取快照。旧锁等待身份可以保留其用途，但不能再用于推导版本提交顺序。
- 实现可验证的 SCN 同步与发布逻辑，包括重复消息验证和等待条件。可先用受控参与者驱动持久化/安装完成事件；这是协议测试，不是声称真实业务写路径已经接好。
- 在测试中使用候选版本描述验证规则，历史内容可以由测试构造。真实业务路径尚未接入时保持边界明确，不在产品路径以“缺 undo 时返回最新行”伪装可用。

### 验收

- 确定性地推进 P0 各并发时序，尤其是低编号提交未完成、高编号消息先到、并发 Begin 与提交发布。
- 同一快照重复判断结果稳定；`commit_scn == snapshot_scn` 可见；同一业务版本的可见性不因锁 owner 改变而改变。
- 少一个必要 ACK、持久化条件或安装完成条件时，提交不得成功。条件全部满足后，跨节点新 Begin 满足读己已提交结果的要求。
- 非法状态倒退、矛盾重复消息、同一事务被赋予不同 commit_scn 等用 assert/CHECK 拒绝。

**退出边界：完成可见性协议与基础组件，不宣称已经能从真实数据页读历史。** 不在本阶段同时实现 undo 缓存、GC 或大规模改造所有负载。

## 5. P2：undo 页、缓存与 redo / replay

### 任务

- 实现逻辑段、写节点子段、按需物理页、页内追加和封口；实现完整逻辑旧行格式、行前驱链和事务逆序遍历所需信息。记录发布后业务内容不可修改。
- 为 undo 分配明确的页身份空间，并接入可增长的页目录与缓冲池路由。不能仅给表号加一个常量，就落入当前索引页“不等待日志”的分支。
- 增加 `undo_buffer_pool_size_pages` 配置及初始化；使用原 BufferPool/LRU 和 LPLM/GPLM 的实际固定、释放、迁移、淘汰流程，不另造 undo 页传输或权限协议。当前另有 `undo_lock_table_initial_capacity`：范围内预分配数组、越界条目按需创建；不把它混同为帧预算。
- 实现 undo 分配、初始化、追加及相关链引用的 redo 编解码；与主行修改一起进入实际写者 WAL。为 P6 的回收/复用留下明确格式边界，回收日志在 P6 实现。
- 存储端识别 undo 页和文件，按已有 WAL 持久化与回放机制重建；覆盖页级前驱、日志流身份和 replay 等待。主行引用 undo 时保留足以判断目标内容已就绪的依赖。
- 区分“redo 已持久化”“redo 已回放”“页可从缓存或远端获得”。没有回放完成时等待正确进度，不将缺页当作历史终点。
- 配合迁移和淘汰建立 WAL 条件：主行及 undo 的依赖必须能被满足，不能丢掉唯一可恢复副本。无需要求每次挂链前都同步落盘。
- 本阶段只追加、不回收、不复用；使用受控数据量验证。缓存帧可以正常淘汰，不得用“不淘汰所有 undo”掩盖持久化缺口。

### 验收

- 只读 Begin 不分配物理 undo 页；多次追加跨页后能按行链和事务顺序分别遍历。
- 极小缓冲池触发反复淘汰，清空计算端缓存后仍能读取已持久化历史。
- 从初始页和持久化 redo 重建 undo 与主行引用；重复回放结果一致；不完整日志尾不被当作完整记录；有完整 undo、尚未挂主行引用时，不误产生业务更新。
- 验证 WAL durable 后、undo 页尚未回放时，GetUndoPage 等准确依赖；孤立 undo 不安装主行。当前 P3 同流主行 redo 必须排在对应 undo 之后，违反顺序应失败。P4 Lazy 的 undo 与主行 redo 仍同 writer；P5 已只对本事务新版本的 redo 强制同 writer undo 依赖，解锁/Release/回滚恢复的完整行 redo 可引用其他 writer 的既有历史。完整跨流恢复等待仍留 P6，不能用错误的同流顺序冒充合法跨流场景。
- 页身份、记录边界、长度、记录完成状态、RID、代次不符时明确失败。针对当前负载核对最大逻辑行大小；若需要跨页记录就明确定义，不能截断或悄悄丢字段。

**退出边界：undo 存储基础可用，不代表所有业务写路径已经生成 undo，也不代表完整事务故障恢复已完成。**

## 6. P3：单节点 Lazy 的真实闭环

当前接入说明见 [LAZY_MVCC_P3.md](LAZY_MVCC_P3.md)。业务 Lazy 已统一新路径；P3 单节点已在 AliYun1 重新验证，P4 两节点见实施交接。下面列的是 P3 退出要求。

### 任务

- 接入 Begin 快照与版本元信息；初始化数据使用明确的初始已提交版本。统一候选版本拷贝与历史重建，读者不修改共享主行。
- 在实际覆盖前生成完整 undo、发布稳定引用，将新业务值、创建者、删除状态和 undo 链头作为一致组合安装。先复制受保护的候选，再释放主数据页保护，逐步获取历史，遵守 P0 的锁顺序。
- 覆盖更新回调与旧私有副本写回两类入口，尤其是 TPC-C 的 `valid=0`；不能只修改 `ApplyWriteOperation` 就认为所有写入已接入。
- 保留 Lazy 执行时安装和延迟物理清锁的模式。全局发布前仍由当前事务阻止其他写者进入；事务终态读取与锁清理不能让版本提前可见。
- 实现自读及重复更新，其他读者能跳过同一事务产生的多条不可见历史。写入前检查最新已提交版本与本快照的关系。
- 以 undo 支撑实际已安装修改的逆序回滚，恢复业务值、创建者、删除标记和旧链头，记录必要 redo；不能把旧锁字节一并恢复。尚未安装的私有写入直接撤销，不伪造主行回滚。
- 保留墓碑和索引入口，确保旧快照能定位历史；可见墓碑是查找终点。

### 验收

以余额 `100 → 90 → 80` 为最小例子：不同固定快照分别读正确版本；未提交写者自读 80、其他事务仍读其可见旧值；重复覆盖后 Abort 完整恢复；过期快照写同一行发生明确冲突。另覆盖删除标记、只加锁不修改、旧写回入口和缓存淘汰后回滚。

检查读者绕过业务行写锁的路径真实生效。页面权限和回放等待仍然允许，不宣称所有读取完全无等待。

## 7. P4：多节点 Lazy、页所有权和历史访问

### 任务

- 接入真实计算节点的 SCN 传播、提交等待与事务状态访问；各节点 Begin 从协议维护的有效边界取快照。
- 对主数据页与 undo 页分别验证 S/X 权限、目录路由、远端取页、所有权转移和 WAL 等待，覆盖正在追加页与封口页。
- 主数据页迁移不改变版本创建事务或 undo 地址；历史页可独立迁移。旧写节点仍可继续事务、追加或回滚，不依赖旧内存地址。
- 同一 undo 页上，A 继续追加、B 读已有记录时正确处理整页权限交接。先确保正确，再记录额外迁移量；不在首版另造不可变记录复制协议。
- 在跨节点状态查询和页面读取期间保留快照保护；暂未实现 GC 时仍不能误注销活跃快照。

### 验收

- A 成功提交后在 B 立即 Begin，B 读到新值；B 先前开始的事务仍读旧值。
- 暂停一个 ACK 或所需日志完成事件，验证提交不会提前成功；乱序提交压力下固定快照不出现新版本。
- 写事务结束前迁移主行页；随后从另一节点读历史、继续更新或回滚。分别淘汰主行页、undo 页、二者同时淘汰后重复验证。
- 强制历史读取与 undo 追加竞争，确认无死锁、无半条记录、无悬空引用，记录权限交接与 WAL 等待。

## 8. P5：2PC、mix 及现有变体

### 任务

- home 私有执行使用同一 snapshot_scn，优先自读私有写集；参与者 Prepare 在写锁保护下验证旧版本、准备完整 undo 及新值，稳定引用附着于 prepared 上下文。
- Prepare YES 的持久化前提覆盖需要的 undo / 新值 redo。Commit 安装主行时引用已准备的 undo，不能再按那一刻的任意主行内容随意生成另一份旧值。
- 所有参与者使用同一事务身份、提交结果和 commit_scn。区分参与者写项安装完成与全事务发布；最后一个参与者完成前，不发布整笔事务，也不把行交给后续写者。
- 结合现有 Prepare 持久化和异步最终日志路径核对 WAL 顺序；不统一增加每页 fsync，也不只因“准备过”就漏掉新格式所需的 undo redo。
- 零写参与者、单本地写参与者、单远端写参与者、多写参与者分别接入。没有 Prepare 的捷径仍要在实际覆盖前保存 undo 并满足其提交持久化条件。
- 普通 2PC、已有 Cornus 及存储通知等分支，按当前配置和实际可达路径逐项核对；mix 的 Lazy 与分布式两条分支都接入，不改造调度策略。
- 远端读取整页后统一执行可见性判断，不能让远端取页入口直接把最新行作为最终结果。

### 验收

以跨节点转账为核心：人为暂停一个参与者安装或提交确认，任何固定快照都只能看到转账前或转账后的完整组合，不能一边扣款、一边未加款；自读、Prepare 前冲突、允许 Abort 阶段的回滚、延迟清锁和锁交接均正确。分别覆盖上述参与者数量与模式分支，并运行相关已有 2PC / 锁等待回归。

本阶段只处理正常运行和已有事务 Abort 流程；不新增宕机后的决议恢复、选主或自动接管，也不把已不可逆的 Commit 决议因超时转换成普通 Abort。

## 9. P6：历史回收、状态保留与页复用（延期、可选）

当前版本只追加，保留全部 undo 历史及可见性所需事务状态；不运行后台 GC、不截断历史链、不复用 undo 页/槽。P5 完成后直接进入 P7。以下任务与验收仅在以后决定实施回收时适用，不是当前正确性门槛；磁盘容量耗尽必须明确停止新写，不能损坏已保留历史。

### 任务

- 将 P1 的快照登记接入全局保留水位；处理 Begin 登记、结束注销、远端执行和水位推进之间的竞态。节点失联不能仅凭超时删除其保护。
- 按最老活跃快照保留每条链所需的边界版本以及更近版本，同时保护未决写事务、回滚、Prepare 上下文和正在遍历的引用。不能简单释放“commit_scn 小于水位”的所有事务段。
- 历史可见性还依赖创建者状态：在所有相关版本不再引用它前保留状态，或先以确定的日志化方式把足够的终态信息落实到版本中，再安全回收状态。
- 实现安全的链尾截断、页回收、页/槽代次与旧缓存副本失效；为相应元数据变化增加 redo 和回放。回滚恢复过的旧链头也要纳入引用安全分析。
- 区分缓存帧压力与磁盘历史压力。缓存满走正常淘汰；历史空间压力限制新写，给在途事务的完成/回滚预留资源。长快照不自动失效。

### 验收

保持一个长快照，同时持续写入、迁移、淘汰、GC 和复用；该快照一直读到原版本。结束它后，空间能够释放。强制复用同一页号时，旧引用不能读成另一行；正常合法读不能因为回收竞态触发代次断言。验证边界版本保留、事务状态回收、未挂链 undo 清理和回收日志重复回放。

## 11. 编码风格：用断言约束内部不变量

这是用户明确要求。项目已经在 [bufferPool](/Users/noctis/Documents/项目/Hybrid_Cloud_MP/core/bufferpool.h:185)、[锁等待与交接](/Users/noctis/Documents/项目/Hybrid_Cloud_MP/core/dtx/lock_wait.h:343)、[2PC 参与者](/Users/noctis/Documents/项目/Hybrid_Cloud_MP/compute_server/twopc_server.cc:312) 大量使用 assert/CHECK。新实现延续这个风格：**内部假设不成立就尽早失败，把出错现场留住，避免层层空值判断、默认值和静默兜底。**

| 位置 | 应明确断言的条件 |
|---|---|
| SCN / 事务 | snapshot_scn 固定；安全边界单调；终态不可倒退；同一事务各参与者的身份和 commit_scn 一致；发布前所有必要条件成立 |
| undo / 主行 | 引用发布前记录完整；长度及页内边界合法；表/RID/代次匹配；版本元信息与业务值一致；覆盖前确有 undo |
| 页面 / WAL | 页种类及路由正确；写入持有必要权限；pin/latch 生命周期正确；迁移/淘汰满足相应 WAL 条件；LSN 比较处于正确日志流或明确依赖关系中 |
| 2PC | Prepare / Commit 属于同一事务及写集；Prepared 内容与 Commit 一致；未全局发布不得提前交出写权限 |
| GC | 被保留快照、在途事务或读者需要的历史不被复用；旧代次不被当新对象；创建者状态仍可解析 |

实施要求：

- `assert` 用于内部前置/后置条件，需在禁用普通断言时仍成立的关键边界用项目已有的 `CHECK` / `LOG(FATAL)`。实际编译选项必须核对；当前根 CMake 设置 Debug / `-O0`，不要想当然地把性能构建中的 assert 当作仍有效。
- 断言不包裹必要副作用。先执行追加、加锁、解码等操作，再断言结果；不能因 `NDEBUG` 导致操作本身消失。
- 对必需配置使用默认值或显式必填规则，并校验合法范围。新格式/新配置不兼容就明确报错；不为尚无需求的旧文件、旧 RPC、旧格式加多层兼容探测。
- 枚举分支、状态转换和页类型写完整；不支持的组合明确失败，不掉回旧的“最新值读取”路径。
- 不用 `catch (...)`、宽泛重试、返回空行、返回最新值、无穷跳过坏记录等方式掩盖断链或协议错误；不为了通过测试删除断言或缩小必要检查。
- 不机械地对所有非成功结果 assert。NO_WAIT / 死锁 / SI 冲突是正常事务结果；页权限或回放尚未就绪要等待；合法墓碑返回不存在；空间压力按约定限流/拒绝。重复 RPC 与重复回放按协议幂等处理，矛盾的重复内容才是错误。
- 正常 RPC/I/O 失败按项目约定明确终止或上报，不伪造成功，不借本轮任务引入一套自动故障接管体系。
