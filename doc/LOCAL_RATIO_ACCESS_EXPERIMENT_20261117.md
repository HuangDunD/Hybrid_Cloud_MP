# Local ratio：获取次数与单次耗时

本轮只改变现有 `local_ratio`，观察 Lazy 的页面/权限获取次数与 2PC 执行路径的 remote fetch 次数是否减少，以及一次获取的耗时。没有新增负载维度、统计埋点或事务协议修改。

## 实验条件

- 代码版本 `b594018`，使用已有服务器二进制；与 `222f178` 相比只有文档变化。
- 开发/存储/remote 为 `172.16.208.1`，计算为 `.2/.3/.4`，四机均有 `erdma_0`；沿用 RDMA、每表 10,000 页数据缓存、buffered 读取、日志开启和 `-O0 -DDEBUG` 构建。
- YCSB，计划每笔 10 次操作、4 读 6 写，θ=0.6，NO_WAIT，每节点 2 worker，每点 30 秒。
- `write_owner_count=0`，恢复原来的局部性生成逻辑。此前固定写者模式会覆盖 `local_ratio`，本轮不使用它。
- `local_ratio` 取 0、0.5、0.9、1；比较 Lazy 与 Cornus。Cornus 使用现有 2PC 的执行取数路径，但本轮不将它的提交结果当成普通 2PC 的测量。
- 第一轮 local ratio 递增、Lazy→Cornus；第二轮整体反向，共 16 次执行。只在服务器运行负载，本地只做静态审查与结果分析。
- 沿用用户之前配置的云盘，不调整 IOPS/BPS；本轮未通过云 API 重新核验配额。不把不同日期的绝对性能变化归因于 local ratio。

`local_ratio` 在当前 YCSB 实现中是事务级生成开关：本地分支的 key 都从当前节点的固定归属数据中选；随机分支逐次随机选择归属节点，也可能选中本地。它不是缓存命中率，也不是精确的远程操作比例。

保留 `FastRand % 100 > LOCAL_TRASACTION_RATE * 100` 的历史判断，所以 0、0.5、0.9、1 对应约 1%、51%、91%、100% 的本地分支概率。没有为本实验顺手修改边界。普通生成路径也保留原来的重复 key 处理，不与固定写者实验的去重生成规则混为一谈。

## 统计口径

主比较采用已有计数：

- Lazy：执行阶段除 `local_ready` 外的六种获取路径之和，表示本次页面调用不能直接按本地已就绪路径完成，仍需获取页面/权限。它包含权限升级、存储取页与回收等待，不等于实际跨计算节点的 RPC 个数。
- 进一步将 Lazy 的 `local_manager + owner_manager + forwarded_page + wait_release` 合为“跨节点相关取页路径”，单独列 `storage_page` 和 `local_upgrade`。前者仍是一次逻辑获页过程，不是报文计数；一次可涉及 manager、回收与推送。权限升级可能只在本地完成，也可能访问远端 manager，因此不能把升级统一判成远程或统一判成本地。
- Cornus：`remote_fetch_success + remote_fetch_conflict`，表示执行阶段 GetDataItem RPC，含请求和回复处理。参与者内部可能继续从存储取页；不能将这里的次数当作整个集群所有网络操作数。
- 每尝试获取次数 = 获取次数 / 完成尝试数；单次耗时 = 获取累计时间 / 获取次数；每尝试累计时间 = 两者乘积。次数为 0 时单次耗时没有样本，标为“—”。
- 耗时包含本地处理、锁/队列等待和通信，不是纯网络 RTT。Prepare、提交日志、最终通知不放进执行访问次数。
- Lazy `local_ready` 的增加不必然全部来自历史复用，也可能是访问本来就本地的数据；只凭 aggregate 统计不能区分二者。
- 额外查看现有存储取页次数和各获取路径，避免把 Lazy 的存储缺页与 Cornus 的计算节点 RPC 当成完全相同的工作。阶段内诊断不可与 execute 时间重复相加。
- 获取计时为整次运行累计，包含启动后的冷缓存访问；没有单独剔除预热。两轮汇总将次数与时间先求和再计算加权均值，不先平均各节点均值。存储取数据页次数来自全阶段计数，可能嵌套在获取过程内，不与主表直接相加。

## 结果

16 次执行全部完成，48 份节点有效配置核对通过，报告无 WARNING、完成数量与统计覆盖一致。运行期间抽查三个计算节点到存储的业务连接，均为 `rdma_state=ON`、`handshake_state=ESTABLISHED`。实验结束后无遗留工作进程，开发源码配置未变。

### 次数与单次耗时

下表 Lazy 只列 `local_manager + owner_manager + forwarded_page + wait_release`，存储取页与权限升级另列。Cornus 列执行阶段 GetDataItem RPC。这是在比较逻辑获取过程，不是双方的网络报文总数，也没有把完整获取时间解释成 RTT。

| local_ratio | Lazy 跨节点相关取页/尝试 | Lazy ms/次 | Lazy 累计 ms/尝试 | Cornus remote fetch/尝试 | Cornus ms/次 | Cornus 累计 ms/尝试 |
|---|---|---|---|---|---|---|
| 0 | 5.886 | 0.1510 | 0.889 | 6.592 | 0.0935 | 0.616 |
| 0.5 | 4.518 | 0.1380 | 0.623 | 3.290 | 0.0932 | 0.307 |
| 0.9 | 1.100 | 0.1358 | 0.149 | 0.589 | 0.0943 | 0.056 |
| 1 | 0 | — | 0 | 0 | — | 0 |

从 0 到 0.9，Lazy 这部分次数减少约 81%，Cornus 减少约 91%。Lazy 单次耗时约下降 10%，Cornus 基本稳定；获取成本下降主要体现为调用次数减少。即使 local_ratio=0 时 Lazy 这四类路径的次数略少，较高单次代价也使其累计等待仍较多；还有表外的存储获取与权限升级需要考虑。

**这也纠正了此前将 Lazy 全部非 `local_ready` 次数简称为“远程访问次数”的说法。** 六类路径的总数可以描述不能直接本地完成的页面调用，但不能直接和 Cornus 的跨计算节点 RPC 数量等同。尤其全本地端点中，Lazy 仍约有 0.98 次这种调用，实际是存储取页与本地权限升级，并没有跨计算节点取页。

### 本地可用、存储取页与升级

| local_ratio | Lazy local_ready/尝试 | Lazy 执行期 storage_page/尝试 | Lazy local_upgrade/尝试 | Lazy 全阶段存储取数据页/尝试 | Cornus 全阶段存储取数据页/尝试 |
|---|---|---|---|---|---|
| 0 | 2.600 | 1.216 | 0.420 | 1.216 | 0.837 |
| 0.5 | 4.061 | 1.076 | 0.451 | 1.076 | 0.761 |
| 0.9 | 7.778 | 0.815 | 0.322 | 0.815 | 0.722 |
| 1 | 9.011 | 0.741 | 0.239 | 0.741 | 0.729 |

本轮 Lazy 的全阶段存储取页与执行阶段 storage_page 数值一致，列出两者是为了说明统计来源不同，不是两份开销。Cornus 存储获取可发生在本地处理或远端参与者处理内部，与 remote fetch 耗时重叠，不能再直接相加。

全本地时，归属本地并不代表缓存里已有页面：两种模式仍约有 0.73–0.74 次存储数据页获取/尝试。Lazy 的权限升级在这个端点由本地处理；其他 local_ratio 下升级可能需要远端 manager，现有聚合计数没有区分该位置，因此主表不声称覆盖所有远端权限请求。

增加 local_ratio 后，Lazy 本地直接完成的调用明显增加，但 aggregate 结果不能将其分解成“原本属于本地”与“之前搬来后的复用”两种收益。Cornus 的固定归属本地事务无需 GetDataItem RPC；Lazy 的归属本地页面则可能已经迁到其他节点。这一机制与中间两档 Lazy 跨节点相关获取多于 Cornus remote fetch 的结果相容，尚未通过逐事务追踪量化各自贡献。

### 完整阶段与吞吐

TPS 为两个独立运行的范围，不是置信区间；执行/提交为两轮累计时间除以两轮累计完成尝试数，包含失败尝试。

| local_ratio | 模式 | Commit TPS 范围 | 执行 ms/尝试 | 提交 ms/尝试 | 回滚率 % |
|---|---|---|---|---|---|
| 0 | Lazy | 2193–2258 | 1.238 | 1.422 | 0.386 |
| 0 | Cornus | 2084–2105 | 0.741 | 2.069 | 0.821 |
| 0.5 | Lazy | 2517–2527 | 0.897 | 1.448 | 0.411 |
| 0.5 | Cornus | 2532–2673 | 0.449 | 1.820 | 0.520 |
| 0.9 | Lazy | 2757–2881 | 0.342 | 1.754 | 0.438 |
| 0.9 | Cornus | 2938–3062 | 0.207 | 1.774 | 0.126 |
| 1 | Lazy | 2749–2836 | 0.177 | 1.940 | 0.423 |
| 1 | Cornus | 2927–2950 | 0.153 | 1.874 | 0.000 |

local_ratio=0 时 Lazy 提交优势抵消执行劣势；0.5 首轮近似持平、第二轮 Cornus 更快；0.9 和 1 两轮均为 Cornus 更快。本轮没有观察到提高 local_ratio 后 Lazy 依靠复用拉开执行优势。全本地的执行差距已较小，剩余吞吐差不能再归因于跨计算节点访问次数。

局部性也改变提交参与者数，不能将吞吐变化全部归因于执行获取。Cornus 进入提交路径的事务中，单写者比例依次为 1.39%、50.84%、91.14%、100%；Lazy 始终集中到单写者。Cornus WAL/成功提交约从 14.14 KiB 降到 7.66 KiB，而 Lazy 各点约 14.6 KiB，沿用现有更新安装与清理日志差异。本轮未修改或单独隔离这些提交因素。

设备监测取节点 TPS 窗口交集内部：各 case 的写 IOPS 均值约 7,754–8,725，读 IOPS 均值最高约 0.71。buffered 模式下的存储 RPC 并不意味着每次产生设备读。客户机设备口径不能直接用于判断云盘限流状态。

## 结论与证据范围

本轮回答了两点：现有 local_ratio 的变化能够明显降低两种方式的获取次数；在当前缓存和写比例下，Lazy 没有因此获得执行优势。它没有回答相同跨分区访问集合下、单独增强未来复用的收益，因为 local_ratio 同时改变原始访问位置与提交参与者分布。

现有统计已经足够描述这次变化，无需新增计数或负载参数。需要保留“跨节点相关取页、存储获取、权限升级”的区别，以及次数和单次代价的乘积；暂不据此制定在线选择规则。没有测试普通 2PC 的额外决议日志开销、长期稳态、完整恢复或新 MIX。
