# 共享存储事务处理的成本边界

更新：2026-11-05。研究题目暂定 **Rethinking Transaction Processing in Shared-Storage Multi-Primary Databases**。

当前目标是先测清成本边界，让模型能够解释、预测选择，再实现并检验自适应策略。
不预设 hybrid 必然胜出；在某个环境、负载范围内，一种静态方法持续占优也是有效结论。
本文件记录研究目标与待验证假设；现有选择器的实际范围见 [实现说明](HYBRID_PAGE_COST_MODEL.md)。

## 合法的执行选择

对远端页面上的访问，可以考虑获得本地可读副本及 S 权限、获得/升级 X 权限后本地执行，
或把操作交给拥有相应权限的节点执行。S 权限可能由多个节点同时持有，X 权限具有排他性；
写操作不能用 S 副本代替 X 权限。已有权限、并发控制和一致性规则先限定候选集合，代价模型只在合法选项中选择。

这些是分析用的候选动作，不表示现有实现已支持在事务中任意切换协议。
先验证事务级选择；更细的逐页/逐阶段选择需要明确锁、提交参与者与恢复责任，不能仅由一个价格比较决定。

“搬页面”和“请对方执行”都不只是一次网络操作。页面带回来会占本地缓存，也会产生后续复用收益；
代执行保留数据局部性，但可能多次调用远端，并增加提交参与者。实际 SQL 的后续访问集合通常运行中才知道，
不能要求内核开发者在一次取页、一次持 latch 期间完成所有业务逻辑。初期先用现有 YCSB/SmallBank
已知访问集合建立可验证基线，之后再处理逐步发现访问、事务内多阶段执行的决策边界。

## 模型需要解释的成本

对候选动作 a，在给定时间范围 H 内预测其边际代价，可以先写成：

`即时执行 + 提交增量 + 冲突/重试 + 缓存占用机会成本 − 未来本地复用收益`。

这是研究分解，不是已经可相加的现有计时列。并行访问和并行持久化应按关键路径建模，
参与者 CPU/IO 工作量另行计算，不能把参与者耗时和协调者等待重复累加。

| 成本 | 需要观测什么 | 必须区分的边界 |
|---|---|---|
| 页面获取 | S/X/升级次数、排队、数据来源、等待日志可见性 | 本地命中、远端缓存、存储读；不把所有权计时当纯网络 RTT |
| 代执行 | 每事务远端调用数、单次等待、参与者内部取页 | 算子粒度与逐记录 RPC；现有 GetDataItem 返回整页，不能假定只发记录 |
| 提交 | 只读、单本地写、单远程写、多写路径 | Lazy、原始 2PC、Cornus 的不同持久化语义；多参与者等待最慢必要证据 |
| IO 资源 | WAL 字节、日志批大小、fdatasync、设备读写 IOPS/BPS/排队 | 逻辑日志数、同步次数、设备请求数不是同一个指标 |
| 缓存空间 | 副本数、工作集、淘汰、缺页、页面后续再用 | 获取本页对其他页面的挤出成本；对方缓存也可能不足 |
| 冲突 | 成功和失败路径时间、重试率、写入失效/权限转移 | 不能只用成功 TPS 或按所有尝试摊低的执行均值 |
| 环境 | 计算 CPU、网络、存储缓存层、介质延迟、限额 | RDMA 同时影响页面迁移和代执行；云盘 IOPS/BPS 与本地盘不同 |

IOPS/BPS 限制既影响单次延迟，也影响并发扩大后的排队。更多持久化参与者意味着更多潜在工作，
但 group commit 会改变实际设备请求量；不能把两份 prepare 直接换算成两倍物理 IOPS。
缓存机会成本可以先用每新增驻留页引起的额外缺页与等待估计，预测范围 H、局部性统计窗口和负载变化速度需实测确定。

## 已有证据和尚缺的证据

[固定 worker RNG 的 51 点实验](WORKER_RNG_STUDY_20261105.md)中，YCSB 只读时扩大每节点缓存
从 10000 页到 40000 页，Lazy 与 Cornus 的胜负反转。它支持“缓存驻留与复用改变选择边界”，
也说明仅用一次页面迁移耗时减去提交开销不足以解释全部场景。

小缓存实验计算节点发生大量淘汰和存储取页，但存储设备稳态读 IOPS 为 0。
已查明取页 RPC 绕过存储 BufferPool，使用普通文件描述符上的 pread，命中 Linux page cache。
因此该结果测的是“计算缓存不足、存储 OS 缓存仍热”的环境，不能当成设备读很便宜或没有取页。
buffered 文件读取同样是从文件读；Direct I/O 的作用是控制这一层缓存，而不是把之前的读取变成“真读取”。

需补充的主要对照：

1. 同一构建、数据布局、worker seed、协议和日志配置下，比较 buffered / Direct I/O。
2. 分别覆盖计算缓存不足和足够、只读和含写；扩大缓存后仍保留的含写差异，再考虑权限迁移、失效和提交重取页。
3. 同时观测设备读写、取页等待、执行和提交，确认差异发生在哪里，并对关键结果反向运行顺序复验。
4. 之后在统一优化构建、不同数据规模/存储架构和硬件上检验边界；现有 `-O0 -DDEBUG` 结果用于定位，不能直接作为峰值性能结论。

## 通用性与在线适应

模型结构应适用于有独立存储进程、共享文件系统等架构；参数来自运行时测量，不假设存在大容量存储端缓存。
没有独立存储服务器也不代表没有缓存：本地文件系统、共享文件系统客户端、文件服务器和设备均可能缓存。
因此必须明确实际绕过哪一层，不能把某一套硬件下的固定阈值推广为通用结论。

后续在线模型应按访问类型、数据来源、提交路径维护近期估计，跟踪样本数、变化和不确定性。
只能看到被选路径会产生选择偏差，需要低频探索或其他可验证的替代路径估计；设置切换滞后，避免在成本接近时反复迁移页面。
当前 EWMA 采样不等于已经解决这些问题。模型先用独立样本预测，再检验预测误差、选择损失和适应时间，
与最好的静态 Lazy / 2PC / Cornus 基线比较，而不是只看 hybrid 总吞吐。

## Direct I/O 对照开关

`config/storage_node_config.json` 的 `local_storage_node.page_read_io` 可设为 `buffered`（默认）或 `direct`。
`test_multi_node.py` 原有配置分发和运行指纹会包含该文件；更改后应新建实验计划，避免覆盖已有 plan 的配置。

- 仅改变 GetPage / GetPageWithLsn 的整页文件读取。direct 使用缓存的独立 `O_RDONLY | O_DIRECT` 描述符，4096 字节对齐缓冲、长度和偏移。
- 数据初始化、元数据读取、日志及回放写入仍走原路径；这不是整个数据库的 Direct I/O 实现。
- Linux/ext4 对同一文件的 buffered 写与 direct 读做一致性协调。读可能等待脏页写回，这部分代价计入 read 调用，需同时观测写 IO。
- GetPageWithLsn 继续检查页面 LSN，未达到要求就重读；读取错误直接报错，不静默退回 buffered。
- storage_timing_stats.txt 与 stats.log 记录模式、读调用/字节/耗时、LSN 重读数。计数只涵盖取页读；read 时间不含 RPC 排队和重试间 sleep，不是完整取页延迟。
- 读耗时总和可以跨并发调用重叠，不是存储服务器的墙钟运行时间。
- O_DIRECT 绕过本机文件数据 page cache，不绕过设备/云存储后端缓存；设备计数表示块设备请求，不是物理介质操作次数。NFS 上还可能仅绕过客户端缓存。

Linux 行为依据：[page cache 文档](https://docs.kernel.org/mm/page_cache.html)、
[open(2) 的 O_DIRECT 约束](https://man7.org/linux/man-pages/man2/open.2.html)、
[内核 direct read 与脏页协调说明](https://docs.kernel.org/filesystems/iomap/operations.html#direct-reads)。
本轮具体环境、验证和测量结果另记实验文档，不能把 direct 模式等同于所有共享存储数据库的必然实现。

本轮结果见 [Direct I/O 与缓存容量对照](DIRECT_IO_COST_BOUNDARIES_20261105.md)。
