# 共享存储事务处理的成本边界

更新：2026-11-06。研究题目暂定 **Rethinking Transaction Processing in Shared-Storage Multi-Primary Databases**。

当前目标是先测清成本边界，让模型能够解释、预测选择，再实现并检验自适应策略。
不预设 hybrid 必然胜出；在某个环境、负载范围内，一种静态方法持续占优也是有效结论。
这份总览整理混合选择需要考虑的因素、已经测出的性能边界和下一步验证顺序，作为共同讨论的入口。
现有早期选择器的实际范围见 [实现说明](HYBRID_PAGE_COST_MODEL.md)；新模型尚未替换它。
详细实验与原始数据索引见 [2026-11-06 回放等待与成本边界记录](REPLAY_WAIT_COST_BOUNDARIES_20261106.md)。

## 当前候选方案

执行方式与提交机制需要分别建模。以下是当前项目的正常路径，不代表完整的 Cornus 容错实现。

| 方案 | 执行方式 | 提交特点 |
|---|---|---|
| Lazy | 获取页面及相应权限，在请求节点执行 | 通常集中到本节点提交；执行期间的页面交接仍可能等待日志 |
| 普通 2PC | 在数据所属节点执行，必要时远程调用 | 多写参与者持久化 prepare，协调者还需持久化决议日志 |
| Cornus | 同样采用 owner-side 执行 | 去掉独立的协调者决议日志等待 |
| Cornus-opt | 同样采用 owner-side 执行 | 在 Cornus 基础上，由存储直接通知 prepare 完成 |

只读、单本地写、单远程写、多写参与者分别走不同提交路径。
只读实验中的 Cornus 主要代表 owner-side 执行，没有多写参与者提交开销。
Lazy 的“单本地写”描述提交归属，其中仍可能包含跨节点页面访问，不能直接与 Cornus 的本地事务子集比较。

在模型中，对一个已有写参与者继续访问，与新增一个写参与者，应具有不同的提交增量。
尚未预先发现完整访问集合的事务，需要随执行更新已知参与者和后续访问估计。

## 合法的执行选择

对远端页面上的访问，可以考虑获得本地可读副本及 S 权限、获得/升级 X 权限后本地执行，
或把操作交给拥有相应权限的节点执行。S 权限可能由多个节点同时持有，X 权限具有排他性；
写操作不能用 S 副本代替 X 权限。已有权限、并发控制和一致性规则先限定候选集合，代价模型只在合法选项中选择。

这些是分析用的候选动作，不表示现有实现已支持在事务中任意切换协议。
先验证事务级选择；更细的逐页/逐阶段选择需要明确锁、提交参与者与恢复责任，不能仅由一个价格比较决定。

“搬页面”和“请对方执行”都不只是一次网络操作。页面带回来会占本地缓存，也会产生后续复用收益；
代执行保留数据局部性，但可能多次调用远端，并增加提交参与者。实际 SQL 的后续访问集合通常运行中才知道，
不能要求内核开发者在一次取页、一次持 latch 期间完成所有业务逻辑。初期先用现有 YCSB/SmallBank
已知访问集合建立可验证基线，之后再处理逐步发现访问、事务内多阶段执行的决策边界。

## 模型需要解释的成本

对候选动作 a，在给定时间范围 H 内预测其边际代价，可以先写成：

`即时执行 + 提交增量 + 冲突/重试 + 缓存占用机会成本 − 未来本地复用收益`。

这是研究分解，不是已经可相加的现有计时列。并行访问和并行持久化应按关键路径建模，
参与者 CPU/IO 工作量另行计算，不能把参与者耗时和协调者等待重复累加。

| 因素怎么变化 | 对 Lazy 的影响 | 对 owner-side 与 2PC 系列的影响 | 需要观测什么 |
|---|---|---|---|
| 本地已有页面和所需权限 | 获取成本低，本地执行更有吸引力 | owner 若在远端，仍可能产生远端调用 | 页面驻留、S/X/升级需求、owner 位置 |
| 页面未来复用增加 | 获取一次页面可以服务后续多次访问 | 逐次远端执行的通信成本可能持续存在 | 再访问频率、复用窗口、失效频率 |
| 缓存相对工作集变小 | 跨分区副本挤占空间，增加淘汰和后续缺页 | 固定 owner 的局部性可能更好；其缓存不足时同样缺页 | 淘汰率、缺页率、工作集、每新增副本的挤出代价 |
| 缺页的数据来源变化 | 从远端计算缓存拿页和从存储读页，成本不同 | 参与者内部取页也受同样影响 | 本地命中、远端计算缓存、存储读取及其等待 |
| 写比例和写热点增加 | 可能增加权限升级、失效、页面迁移和提交重取页 | 可以减少页面迁移，但行冲突和 owner 排队仍存在 | 读写比例、权限交接、冲突位置、提交重取页 |
| 写参与者数量增加 | 执行可能访问更多远端页面，但提交仍可能集中 | 多写提交等待及总工作量变化，新增参与者有边际成本 | 提交路径、参与者集合、prepare 与决议日志关键路径 |
| 并发增加 | 日志合批收益、权限竞争和资源排队一起变化 | 参与者日志也能合批，不能按逻辑日志份数推算物理同步次数 | 批大小、同步次数/成功事务、队列、各阶段等待 |
| 存储同步时延或 IOPS/BPS 变化 | 影响提交、缺页及回放等待 | 影响多参与者持久化和参与者内部缺页 | WAL 字节、fdatasync 时延、设备读写请求/字节和排队 |
| 网络和远端执行粒度变化 | 影响搬页成本；搬来后可以继续本地操作 | 影响每次 RPC 成本及总调用数；单次远端执行完成多少工作很关键 | RTT、字节数、RPC 数、算子粒度、事务内访问轮数 |
| 失败位置及 owner 负载变化 | 失败前可能已经支付页面获取成本 | 可能较早发现冲突，也可能被繁忙 owner 拖慢 | 失败尝试耗时、锁等待、各节点 CPU 与服务队列 |

表中是有条件的变化方向。读热点可能提高副本复用，写热点则可能增加权限争夺，不能只用一个 θ 概括。
回滚比例也不足以描述重试代价；需要同时知道一次失败已经消耗多少工作。
当前 GetDataItem 按记录请求但返回整页，不能将它当成只返回记录或完整远端算子的通信成本。

IOPS/BPS 限制既影响单次延迟，也影响并发扩大后的排队。更多持久化参与者意味着更多潜在工作，
但 group commit 会改变实际设备请求量；不能把两份 prepare 直接换算成两倍物理 IOPS。
缓存机会成本可以先用每新增驻留页引起的额外缺页与等待估计，预测范围 H、局部性统计窗口和负载变化速度需实测确定。

## 已测到的性能边界

下面是三个计算节点的总稳态 Commit TPS，worker 和缓存容量均指每节点，缓存按每表配置。
实验使用 RDMA、每点 45 秒、NO_WAIT、日志开启及当前 `-O0 -DDEBUG` 构建；存储为用户设置的 20000 预配置 IOPS 档位。
这些数值用于比较成本边界，不是优化构建后的峰值，也不是新混合策略的实测性能。

含写 YCSB 默认 θ=0.6、write_ratio=0.8、local_ratio=0.5，表中明确标出的条件覆盖默认值。
SmallBank 的 write_ratio=0.8 指写事务类型比例；YCSB 则指事务内写操作比例。
“—”表示这轮没有测该组合。Cornus-opt 尚未覆盖这轮完整矩阵。

### 并发和提交机制

| 场景 | Lazy TPS | 普通 2PC TPS | Cornus TPS | 当前观察 |
|---|---|---|---|---|
| 1 worker，1 万页，buffered | 2409 | — | 2085 | Lazy 的提交优势占主导 |
| 2 worker，1 万页，buffered | 3487 | 3028 | 3665 | Cornus 开始领先，接近边界的点需更多重复 |
| 8 worker，1 万页，buffered | 10876 | 9511 | 11813 | 提交机制改变胜负 |
| 8 worker，1 万页，direct | 6481 | 7108 | 7184 | 存储压力下普通 2PC 与 Cornus 吞吐接近 |
| 8 worker，4 万页，buffered，θ=0.95 | 3274 | — | 7351 | 缓存足够后，热点差异仍存在 |
| 8 worker，4 万页，buffered，全本地 | 17151 | — | 17104 | 两种方式接近 |
| SmallBank，8 worker，1 万页，buffered | 29357 | — | 27953 | 当前工作集下 Lazy 略占优 |

以 8 worker、1 万页、buffered 为例，成功事务的全程阶段均值如下。TPS 与设备指标取截取窗口，阶段均值取全程；不能直接混用两种窗口套吞吐—延迟关系。

| 模式 | 成功执行 ms | 成功提交 ms |
|---|---|---|
| Lazy | 0.932 | 1.177 |
| 普通 2PC | 0.390 | 2.016 |
| Cornus | 0.400 | 1.527 |

普通 2PC 节省的执行时间，被额外提交成本抵消；Cornus 降低提交成本后，整体超过 Lazy。
小缓存 direct、高并发时，普通 2PC 提交更慢但执行等待更少，吞吐与 Cornus 接近。
这支持提交节奏与取页/回放排队相互影响的解释，具体因果贡献仍需单独消融。

并发还会改变物理同步需求。buffered、1 万页的首轮扫描中，1 worker 时每成功事务对应
Lazy/Cornus 约 1.02/1.97 次 fdatasync，8 worker 时降到约 0.40/0.32 次。
这些是全程同步总数除以成功事务数，包含参与者和失败尝试的工作，不是单笔事务的协议轮数。

### 缓存容量和页面来源

固定只读 YCSB、θ=0.6、local_ratio=0.5、8 worker、Direct I/O：

| 每表每节点缓存页数 | Lazy TPS | owner-side TPS（Cornus 模式） |
|---|---|---|
| 10000 | 9122 | 43667 |
| 16000 | 26043 | 64039 |
| 32000 | 190257 | 63711 |
| 40000 | 228766 | 64232 |

只读时没有多写参与者提交，这组主要反映执行和缓存行为。16000 页时，owner-side 已没有淘汰和稳态设备读；
Lazy 仍有较多副本淘汰。32000 页时 Lazy 已经反超，但全程仍淘汰约 53 万页，稳态设备读仅约 0.22 IOPS，
其他计算节点缓存承接了大量剩余缺页。因此，**本地缺页不等于需要访问存储**。

模型至少区分本地命中、远端计算缓存命中、需要存储读取三个层次，再区分存储读取命中 OS 缓存还是进入设备路径。
此前 buffered 小缓存实验的零设备读来自存储 OS page cache；这里 direct 下的近零设备读有不同原因。
buffered 也是文件读取；Direct I/O 仅用于控制该层缓存，并不代表绕过所有设备或后端缓存。

### 冲突和事务局部性

热点组两边失败比例均约 52%，但失败尝试平均总耗时，Lazy 约 3.45 ms，Cornus 约 1.39 ms。
只比较失败率会遗漏这部分执行代价；成功与失败路径需要分开估计。

全本地、1 worker 时，Lazy 与 Cornus 的成功提交均约 0.59 ms，执行也接近；8 worker 时吞吐也接近。
混合负载中单本地写路径的等待，需要结合其他远端参与事务的并发工作和资源状态分析。
这个控制同时改变了远端访问和提交参与情况，不能单独归因于某一项。

### 网络和提交变体的证据范围

[早期 TCP 与 eRDMA 对照](RDMA_TCP_EXPERIMENT_20261105.md)表明两种执行方式都能受益于网络提速，
TPS 收益取决于通信次数及日志等其他瓶颈。该实验早于本轮 RNG 修复和回放等待改动，不把其绝对 TPS 混入上表。
Cornus-opt 在早期短测中没有显示相对 Cornus 的稳定吞吐优势，还需在当前版本补齐对照。

事务大小、实际写参与者数量、远端算子粒度、owner 负载不均衡，以及当前版本下的多档 IOPS/BPS 对照，尚未形成完整性能曲线。

数据来自 [76 点实验记录](REPLAY_WAIT_COST_BOUNDARIES_20261106.md)及
`result/replay_wait_study_20261106/metrics.json`。含写表依次选取 repeat/006、scaling/008、repeat/002、
repeat/004、controls/009、locality/004、controls/013 等对应配置；普通 2PC 与 Cornus 使用相同配置配对。
首轮扫描与最终复验的版本区别、完整 case 索引和原始配置保留在实验记录中。关键点有复验，完整矩阵不是置信区间估计。

## 混合方法的目标与验证顺序

当前实测定义了需要追赶的静态基线。新策略的真实 TPS 必须包含决策、探索、切换和缓存状态变化的开销，
不能把不同实验的赢家数值拼成混合策略的性能。对不同事务选择不同路径可能带来额外收益，需要实际混合运行验证。

第一版模型优先抓三类成本：缓存获取与后续复用、实际提交路径增量、失败尝试代价。
网络、批量大小、存储排队和 owner 负载作为动态条件，避免为一种协议设置跨场景不变的代价常数。

| 顺序 | 要回答的问题 | 完成判断 |
|---|---|---|
| 离线选择预测 | 能否预测缓存、并发及提交变体引起的胜负反转 | 在独立样本上评价预测误差与选择损失，不用同一批耗时拟合后自证 |
| 提交变体补齐 | Cornus-opt 在当前版本中何时有额外收益 | 与 Cornus 配对比较提交路径、通知成本和 TPS |
| 关键维度补测 | 参与者数、事务大小、执行粒度和 owner 负载如何改变边界 | 每次单独改变一个主要因素，记录执行、提交、失败和资源需求 |
| 在线混合运行 | 选择和切换后是否仍有收益 | 对比同条件下最优静态方案，测适应时间、切换开销和稳定性 |
| 通用性验证 | 是否依赖当前构建、存储缓存或云盘 | 统一优化构建，扩大数据规模，再换存储环境与硬件 |

## 通用性与在线适应

模型结构应适用于有独立存储进程、共享文件系统等架构；参数来自运行时测量，不假设存在大容量存储端缓存。
没有独立存储服务器也不代表没有缓存：本地文件系统、共享文件系统客户端、文件服务器和设备均可能缓存。
因此必须明确实际绕过哪一层，不能把某一套硬件下的固定阈值推广为通用结论。

后续在线模型应按访问类型、数据来源、提交路径维护近期估计，跟踪样本数、变化和不确定性。
只能看到被选路径会产生选择偏差，需要低频探索或其他可验证的替代路径估计；设置切换滞后，避免在成本接近时反复迁移页面。
当前 EWMA 采样不等于已经解决这些问题。模型先用独立样本预测，再检验预测误差、选择损失和适应时间，
与最好的静态 Lazy / 2PC / Cornus 基线比较，而不是只看 hybrid 总吞吐。

## Direct I/O 对照开关

`config/storage_node_config.json` 的 `local_storage_node.page_read_io` 可设为 `buffered`（默认）或 `direct`。
`test_multi_node.py` 原有配置分发和运行指纹会包含该文件；更改后应新建实验计划，避免覆盖已有 plan 的配置。

- 仅改变 GetPage / GetPageWithLsn 的整页文件读取。direct 使用缓存的独立 `O_RDONLY | O_DIRECT` 描述符，4096 字节对齐缓冲、长度和偏移。
- 数据初始化、元数据读取、日志及回放写入仍走原路径；这不是整个数据库的 Direct I/O 实现。
- Linux/ext4 对同一文件的 buffered 写与 direct 读做一致性协调。读可能等待脏页写回，这部分代价计入 read 调用，需同时观测写 IO。
- GetPageWithLsn 先等待该页已回放且可见的 LSN，再读取整页并校验；不通过反复读页等待版本，也不把 WAL durable 当作页面已就绪。读取错误或版本不满足直接报错，不静默退回 buffered。
- storage_timing_stats.txt 与 stats.log 记录模式、整页读调用/字节/耗时、回放等待次数及累计耗时。旧结果仍保留 LSN 重读数。read 时间不含回放等待和 RPC 排队，不是完整取页延迟。
- 读耗时总和可以跨并发调用重叠，不是存储服务器的墙钟运行时间。
- O_DIRECT 绕过本机文件数据 page cache，不绕过设备/云存储后端缓存；设备计数表示块设备请求，不是物理介质操作次数。NFS 上还可能仅绕过客户端缓存。

Linux 行为依据：[page cache 文档](https://docs.kernel.org/mm/page_cache.html)、
[open(2) 的 O_DIRECT 约束](https://man7.org/linux/man-pages/man2/open.2.html)、
[内核 direct read 与脏页协调说明](https://docs.kernel.org/filesystems/iomap/operations.html#direct-reads)。
本轮具体环境、验证和测量结果另记实验文档，不能把 direct 模式等同于所有共享存储数据库的必然实现。

早期结果见 [Direct I/O 与缓存容量对照](DIRECT_IO_COST_BOUNDARIES_20261105.md)。
后续修复与并发/缓存对照见 [回放进度等待与成本边界](REPLAY_WAIT_COST_BOUNDARIES_20261106.md)。
含写小缓存 direct 的旧版结果存在读盘轮询放大，不能用它标定正常提交或代执行成本。
新对照也表明：低并发时 Lazy 的提交优势可以占主导；并发扩大后，日志批量合并与执行成本改变胜负。
提交参数应随实际批量、排队和参与者路径更新，不能仅凭协议日志份数推算设备 IO 需求。
