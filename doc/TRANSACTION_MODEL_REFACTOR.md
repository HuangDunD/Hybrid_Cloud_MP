# 事务执行与提交模型改造

状态：实现交接说明，尚未实施。2026-11-06 讨论后收窄第一轮范围，由师弟推进。代码基线为 `0eade81`，已同步本地、GitHub 和开发机；本文的同步与提交状态另行记录。

第一轮先改清楚 YCSB、SmallBank 的 workload：业务代码明确表达读取、计算和更新，执行阶段把更新安装到页面，提交阶段不再首次写入业务值。完成必要的读可见性检查和回滚后，可以先保留逐页清锁作为过渡。

后续方向才是统一更多入口，以及通过事务终态取消提交时必须取齐页面的清锁流程。页面的短期 latch 与跨节点所有权仍由现有页面层管理。

先建立可比较的事务执行基线，再继续研究 Lazy 与 owner-side execution 的成本模型。已有[成本分解实验](LAZY_2PC_COST_ATTRIBUTION_20261106.md)描述的是旧事务模型的实际行为；其提交取页成本不能直接当成所有权转移架构的固有成本。

## 第一轮交给师弟的任务

### 范围与顺序

1. 先梳理 YCSB 的 `AddToReadWriteSet → TxExe → 修改 DataItem 副本 → TxCommit` 路径，在现有 DTX 中抽出明确的记录读取、更新操作。
2. 先在 Lazy 路径让 `Update` 真正安装业务值，并完成旧值保存、日志、读取冲突检查和失败撤销。不能只把整个提交写回循环换个名字移到 `Commit` 前面。
3. 用 SmallBank 转账等业务接入同一接口，验证先读取多条记录、进行计算、再更新的自然写法。同一事务允许多次读写同一记录。
4. 上述路径验证后，再对齐 owner-side 执行和 2PC/Cornus 系列：更新由参与者在执行阶段安装，Prepare/Commit 不重复应用业务更新。具体远程 RPC 划分单独记录后实施。

第一轮主体是前三步。第四步是随后用于恢复公平性能对比的衔接任务；在对齐前，不把新 Lazy 与旧远程路径的吞吐差异作为架构结论。不要让只支持部分模式的新接口静默落回旧的延迟写回语义，应明确记录各模式的接入状态。

本轮不展开 SQL 执行器整体改造、TPCC 迁移、完整 MVCC、TIT/事务终态服务、延迟清锁、单边 RDMA 状态查询或新的混合决策模型。SQL 已有的旧值保存和回滚代码可以复用，但这些后续功能不是第一轮的交付前提。

### workload 应该怎么写

以下为语义示意，不是要求照搬 API 名称：

```cpp
Begin();
auto a = ReadForUpdate(account_a);
auto b = ReadForUpdate(account_b);
if (a.balance >= amount) {
    a.balance -= amount;
    b.balance += amount;
    Update(account_a, a);  // 此时安装到页面，保存旧值并生成日志
    Update(account_b, b);
}
Commit();                 // 完成提交，不再首次安装上述业务值
```

workload 负责业务判断，DTX 负责页面访问、记录锁、旧值和日志。读操作返回的业务值可以是副本，关键是修改副本后必须有明确的更新调用，不能依赖提交时自动发现并写回。实际接口必须处理每一步失败，并回滚整笔事务；示例省略了错误分支。

不要求业务在一次页面访问内完成全部计算，也不允许把 latch 一直拿到下一次业务调用。YCSB 的简单单条读改写可以提供短小的合并操作，减少重复取页；SmallBank 的跨记录计算允许先读后写。保留现有业务条件，例如余额不足时提交但不修改余额。

### 第一轮必须一起解决的语义

- 提前写页后，其他事务的读写必须检查冲突，不能继续直接读取活跃写者的新值。第一版优先沿用已有等待/NO_WAIT 策略处理，明确实际读取规则；不以尚未实现的 `UndoDataItem` 版本回溯作为前提，也不声称已实现完整 MVCC。
- 旧值必须在覆盖前保存；后续更新失败时，撤销已经安装的修改。同一记录反复更新、自读自写和整笔回滚均需正确。
- 可以保留提交时的逐页版本补记和清锁，但不能再次安装业务值。复核解锁、提交持久化与对外可见的先后关系，不能因沿用旧循环而提前暴露尚未满足提交条件的更新。
- 沿用并检查 WAL、页面迁移与日志回放的依赖，不把每次 `Update` 变成一次同步刷盘。进程内回滚通过不代表崩溃恢复已经验证；恢复支持范围必须如实记录。

### 交付与验收

在现有服务器环境验证，复用现有入口和 `stats.log`，不另加本地模拟测试框架或根目录测试脚本。

| 验收项 | 要看到的结果 |
|---|---|
| 更新时机 | `Update` 返回成功时业务值已安装；`Commit` 不再首次应用它 |
| 提交与回滚 | 成功值正确；第二次操作失败时，第一次已经安装的修改也被撤销 |
| 重复访问 | 同事务读取自己刚写的值；同 key 多次更新后回滚到事务前的值 |
| 并发读写 | 两个事务交错时不读未提交值、不覆盖其他活跃写者 |
| 页面迁移 | 更新后、事务结束前页面迁走，后续访问与回滚仍正确 |
| SmallBank | 转账结果、余额不足的无修改提交和失败撤销均符合原业务含义 |
| 成本核对 | 复用执行/提交/回滚时间及取页、RPC、日志指标；比较总成本，不只展示提交变短 |

建议先交付一版 YCSB 的接口与正确性结果，再接 SmallBank。每版在本文追加：提交号、已接入模式、服务器结果路径、实际读取/冲突规则、验证结论和未覆盖项。后续模式未对齐或恢复未验证时直接注明，不把第一轮完成写成整个事务模型改造完成。

## PolarDB-MP 的参考与后续方向

PolarDB-MP 在行上保存全局事务身份，通过事务信息表 TIT 判断事务状态；页面权限 PLock 与行锁 RLock 分工。其提交过程会为仍在缓冲区的相关行补记提交时间戳，未补记时可通过 TIT 查询；读取旧版本则依赖 MVCC 和 undo。这说明业务更新、事务结果与页面清理可以分离，也支持“本地能顺手清理就清理”的方向。参考原论文 [§4.1 Transaction Fusion、§4.3 Lock Fusion](https://zhangyingqiang.com/paper/PolarDB_Multi_Primary.pdf)。

第一轮只借鉴这些职责划分，不照搬完整 PMFS、TIT 或单边 RDMA 机制。下面保留完整改造背景与后续设计，供接口选择时参考，不要求本轮全部实现。

## 完整改造的方向

- 业务更新在执行阶段安装，不再默认集中到事务提交阶段写回。
- 事务结束不必逐页擦除记录上的锁标记；后续访问者能够根据持锁事务的终态判断锁是否仍然有效。
- 提交结果确定后，可以顺手清理仍在本地且可立即修改的页面；清理成功不是提交完成的必要条件。
- workload 使用明确的记录读写接口，页面访问、逻辑锁、旧值和日志由共同实现处理。
- 支持逐步发现访问集合、读取结果决定后续操作和同一事务重复更新，不要求提前知道完整读写集。
- 页面 latch 只覆盖局部操作。不能为了避免第二次取页，将它一直持有到业务计算结束、下一条客户端语句或事务提交。

暂不把 Oracle ITL 的具体块布局作为前提。先保留行上的事务引用，建立可靠的状态判定；是否把同页事务信息集中到槽位中，可以在语义统一后再决定。

## 当前存在的三条路径

| 入口 | 数据安装时机 | 事务结束方式 | 主要代码 |
|---|---|---|---|
| YCSB、SmallBank benchmark | `TxExe` 取出私有副本，业务修改副本，`TxCommitSingle` 写回页面 | 逐记录写回、填写提交时间戳、解锁，最后等待结束日志 | [YCSB](../workload/ycsb/ycsb_db.h)、[DTX](../core/dtx/dtx_exe.cc) |
| `interactive ycsb/smallbank` | 每条请求先解析整笔事务的操作，然后沿用上述私有副本路径 | `TxCommit` | [RunInteractiveBench](../compute_server/worker/worker.cc) |
| SQL `BEGIN/UPDATE/COMMIT` | `UpdateExecutor::Next` 已在执行语句时直接修改页面 | `TxCommitSingleSQL` 仍重新取页处理时间戳、锁和部分删除收尾 | [UpdateExecutor](../core/sql_executor/execution/ExecutorUpdate.h)、[RunSQL](../compute_server/worker/worker.cc) |

交互式 benchmark 的“一行命令包含多个操作”与 SQL 的“多条客户端语句共享一个事务”是不同入口。TPCC 也已经有多次 `TxExe`、逐步增加访问项的用法，不能按 YCSB 的一次取齐模式改死接口。

SQL UPDATE 会保存修改前的业务值到 `WriteRecord`，`TxAbortSQL` 按逆序恢复。这部分可作为共用更新、回滚原语的起点。私有写集本身并不等价于 OCC；当前 benchmark 已经同时使用记录锁和延迟安装。

下列现有能力不能直接视为新模型已经具备：

| 当前实现 | 改造时必须补齐的含义 |
|---|---|
| `write_set` 保存进程内旧值 | 只能支持相应进程存活时的回滚，仍需核对持久化 undo 和恢复链 |
| `UpdateLogRecord` 支持可选旧值 | 当前 `ComputeServer::AddUpdateLog` 传入的旧值参数为 `nullptr`，不能因此宣称更新日志已有完整 before-image |
| `TxCommitOver`、`TxAbortOver` 都生成 `BatchEndLogRecord` | 该记录自身没有 COMMIT/ABORT 结果字段，不能直接作为可查询的事务终态 |
| `lock_wait_mgr` 的 `active_txs_` | 是等待管理的活跃集合；`FinishTx` 删除条目，不是持久的 COMMITTED/ABORTED 状态表 |
| `UndoDataItem` | 当前函数直接返回输入，没有实现历史版本遍历，不能以此声称已有完整快照读取 |

对应实现见 [日志生成](../compute_server/server.cc)、[结束日志](../core/dtx/dtx_log.cc)、[日志格式](../core/storage/log_record.h)、[等待管理](../core/dtx/lock_wait.h)、[版本读取](../core/dtx/dtx.cc)。

## 分清三种保护

| 保护 | 解决的问题 | 生命周期 |
|---|---|---|
| 页面 latch 与 pin | 页面内存、结构和一次局部修改的安全 | 局部访问期间 |
| 跨节点页面所有权 | 哪个节点可以访问或修改页面副本 | 由现有页面协议授予、回收 |
| 事务记录锁与可见性 | 其他事务是否可以读取或修改一条记录 | 由事务状态及所选隔离规则决定 |

释放 latch 后，记录锁仍可有效；页面转移到其他节点后，记录中的持锁事务身份仍必须可解释。事务提交后，行上留下该事务的标记，也不表示它仍持有有效锁。

本地已有页面并不保证获取 latch 不等待。新模型保留这部分真实争用成本，不通过延长 latch 生命周期来人为减少取页计数。

## 共用记录操作

以下名称表达接口职责，尚不是已添加的 API：

| 操作 | 职责 |
|---|---|
| `Read` | 按统一可见性规则读取值，返回独立于页面地址的结果 |
| `ReadForUpdate` | 取得逻辑写锁并读取当前值，返回值及逻辑记录句柄 |
| `Update` | 核对本事务的写权限，记录旧值，安装新值并生成日志 |
| `Commit` | 固定提交集合，完成持久化条件，发布事务提交结果并唤醒等待者 |
| `Abort` | 撤销已安装修改，完成回滚所需的日志和状态转换，再唤醒等待者 |

句柄可以携带表、key、RID 和必要的身份信息，但不能让业务代码跨越页面释放继续使用页内指针。需要处理 RID 失效或槽位复用时，应由记录层重新定位或验证。

一次更新的共同逻辑为：

```text
定位记录并获取短期页面保护
    → 判断持锁事务状态，取得或确认本事务的逻辑写锁
    → 保存本次修改前的值及恢复所需信息
    → 安装新值，保持记录指向尚未提交的事务
    → 生成相应日志，建立页面与日志的依赖
    → 释放短期页面保护
```

日志必须遵守 WAL 约束：不能让尚无可靠恢复依据的修改成为可持久化、不可撤销的页面状态。它不意味着每次 `Update` 都同步刷盘；提交、页面落盘及跨节点交接时如何保证依赖，需要沿用并审查现有日志协议。

简单的读改写可以提供短小的合并操作，在一次页面访问中完成。涉及其他记录或其他语句的计算，允许先读、稍后再调用更新；此时第二次访问可能是必要的。不要把整个业务事务放进一个持有页面 latch 的回调。

仅增加 `ApplyWrites`，把提交循环挪到 `TxCommit` 之前，不作为最终完成标准。它仍可能是“取页拷贝、释放页面、再次取页写回”，只是改变了时间分解的归属。

## 事务状态与逻辑解锁

建议由事务 home 管理权威状态；其他节点可查询并缓存已经确定的终态。记录引用的事务身份优先复用现有 `TxnIdentity` 的节点、进程代次和本地事务号组合，避免另造一套会在重启后混淆的标识。

```text
ACTIVE → COMMITTING → COMMITTED
ACTIVE → ABORTING   → ABORTED
```

`COMMITTING`、`ABORTING` 都不能被当成已释放的锁。分布式参与者的 `PREPARED` 是独立的协议状态，不等于全局 COMMITTED，也不允许参与者自行选择相反结果。

写访问发现记录引用其他事务时：

- 活跃或尚未完成：按选定的 NO_WAIT 或等待策略处理；等待时释放页面 latch，再重新定位和校验。
- 已提交：旧写锁逻辑失效，可以在当前页面访问中清理旧标记或登记新持锁者。
- 已回滚：确认该记录上的未提交修改已撤销，或有明确的版本跳过规则，然后继续。
- 状态未知或查询失败：不能将“查不到”解释为已提交、已回滚或锁已释放。

后续访问者查询并清理属于新路径的成本。终态缓存可避免重复 RPC，缓存也必须遵守事务身份与状态回收规则。只缓存已确定终态不需要把它重新变成 ACTIVE，但仍需防止旧 ID 复用和过早删除状态。

原有等待队列还依赖逐记录解锁和过户，`FinishTx` 有相应检查。改成事务级终态通知时，应一起调整登记、唤醒和重检流程，不能仅跳过旧解锁循环后继续调用原 `FinishTx`。

### 提交时顺手清理本地页面

不强制逐页清锁，不代表提交时完全不清锁。事务的全局提交结果已经确定后，可以利用已有写集中的页面标识，尝试清理本地页，减少后续访问的状态查询和补记工作。同一页面中的多条记录尽量一次处理。

- 页面仍在本地缓存，当前节点具有修改权限，并且可以立即取得短期 pin/latch，才执行清理。本地存在副本不等于仍持有排他权限。
- 在页面保护下重新核对记录引用的完整事务身份，只清理本事务留下的标记，不能擦掉后来事务已经取得的锁。同时补记需要保留的提交时间戳或版本信息。
- 页面不在本地、权限已转移或 latch 正忙就跳过；不为清理发起磁盘取页、远程所有权申请或等待。使用不会隐式触发这些操作的本地尝试接口。
- 清理后的页面与日志仍须满足恢复和页面交接规则；不能仅擦除事务引用却丢失版本解释依据。清理不应引入一次额外的同步刷盘等待。

这种清理是可省略的优化。即使全部跳过，其他事务也必须能依靠已确定终态正确访问记录，等待者也必须能被唤醒。回滚只有在相应更新已撤销后才能清理，不能套用提交后的直接解锁。

第一版可尝试当前写集的本地页面；如果大事务中扫描本身成为明显开销，再考虑限制清理工作量。比较时同时记录本地清理成本与后续访问节省，不能只看提交阶段。owner-side 参与节点也采用同样的本地清理原则。

## 提交与回滚的边界

提交前，已经执行的业务更新必须完成安装，必要日志必须可恢复，参与集合与操作边界必须封闭。满足协议的持久化条件后，再发布 COMMITTED 和提交时间戳。其他事务不能仅凭某一条记录已写入新值就把它视为已提交。

当前逐记录填写的 `version/commitTimeStamp` 也要迁移语义：提交时不能为了填这些字段又遍历所有页。访问者需要能从事务引用取得提交信息，并在适当时机补记到页面；相关读取、日志回放及页面转移路径必须使用相同解释。

第一版回滚建议保持明确的完成顺序：ABORTING 期间保留冲突保护，逆序撤销已安装的更新并完成恢复所需记录，之后才发布可供后续写者继续操作的 ABORTED。若以后希望提前公布逻辑回滚决定，需要单独区分“决定已确定”与“撤销已完成”。

因此，不逐页清锁主要消除提交的强制遍历；执行时安装更新后，回滚仍可能需要获取和恢复多个页面。减少提交取页可能增加失败工作，必须同时测量。

同一事务多次更新同一记录时，须支持读取自己的新值并正确撤销更新序列。第一版可复用逐次记录旧值、逆序恢复的方式；后续再考虑首个 before-image 合并，不能仅按 key 去重就丢失回滚语义。

## 读可见性与共享读锁需要先确定

提前安装更新会把未提交值放进共享页面，因此不能保留原有 benchmark 的读取方式而只修改写路径。当前读取依赖的 `UndoDataItem` 尚未实现版本回溯，必须明确其他事务遇到活跃写者时是等待、回滚还是读取旧版本。

这是第一阶段接口落地前需要确定的语义，而不是新增一个随意切换的配置开关：

| 方案 | 需要的实现 | 对实验的影响 |
|---|---|---|
| 基于锁的读取 | 明确读锁的持有期及共享持有者身份，按事务终态判定其有效性 | 与写者存在读写冲突；强隔离的范围查询还需额外处理 |
| 基于版本的读取 | 可用的旧版本、事务状态、快照边界和版本回收 | 读者可绕过未提交新值，但不能仅有 undo 字段而没有完整读取规则 |

SQL 当前存在 `read_keys` 和行内共享锁计数，提交时会逐条减计数。一个写者的 TxnId 不能代表多个读锁持有者；如果保留这种读锁语义，就需要可解释的共享持有者信息，不能简单删除减计数循环。

第一版至少保证不读到其他事务的未提交值、自读自写正确及写写互斥。是否要求事务级快照或可串行化，需要在两条执行路径使用相同规则后再命名和评价，不能把上述最低条件直接称为完整的某个 SQL 隔离级别。

## Lazy 与 owner-side 使用相同事务语义

Lazy 在获取页面权限的执行节点安装更新；owner-side 在拥有页面的参与节点安装更新。共用的是记录操作、可见性和回滚规则，保留页面放置和提交协调方式的差异。

当前远程路径先返回数据给 home，在 Prepare 中携带最终写集，最终 Commit 处理页面写入。提前安装后必须重新划分：执行 RPC 安装未提交更新，Prepare 固定并持久化必要证据，最终 Commit 根据全局结果发布状态，避免再次应用业务更新。

若业务计算仍在 home，读结果返回后可能还需要一次更新 RPC；若使用远程算子，则取决于算子能否在 owner 完成这一步。不能默认它免费合并，也不能为了有利于某一种模式而隐去这次通信。

普通 2PC、Cornus 和存储通知版均需使用一致的执行模型再比较。已有 Prepare 完整写集日志和通知处理可以复用，但不能仅因执行时已写页，就删掉持久化投票或恢复所需证据。多写事务的状态发布仍须对应唯一的全局决议，不能把每个参与者独立结束当成原子提交。

远程操作的事务身份与操作序号应支持重试识别，并拒绝事务封闭后的迟到更新。先复用现有协议身份与请求生命周期，避免再维护一套互不相干的事务信息。

## 完整改造路线（区分本轮与后续）

| 阶段 | 工作内容 | 完成判断 |
|---|---|---|
| 1 接口与语义 | 明确读取规则；抽出记录更新和旧值管理；YCSB 首先使用显式读写操作 | 业务层不再依靠随意修改私有指针等待提交自动写回；接口允许分阶段访问 |
| 2 执行时安装 | Lazy 更新在执行阶段安装，补齐读取检查和回滚；过渡阶段可保留旧提交清锁 | 提交前页面已有未提交修改；其他事务不会误读；失败能恢复旧值 |
| 3 SmallBank 接入（本轮） | 使用同一接口实现跨记录读取、计算、更新 | 转账、无修改提交、重复访问与失败撤销正确 |
| 4 对齐远程路径（随后） | owner-side 执行时更新，适配单写、多写和三种提交变体；接入交互式 benchmark | 同样的业务和隔离规则下比较真实执行、提交和回滚成本 |
| 5 状态化结束（后续） | 引入可查询终态及其日志，调整版本字段、等待队列和状态回收；取消必须取齐页面的清锁流程，保留本地顺手清理 | 页面已迁走时也能结束事务；后续访问可正确识别旧锁标记 |
| 6 统一其他入口（后续） | 接入 SQL UPDATE 与多阶段 TPCC，再处理 INSERT/DELETE 和索引维护 | 多语句事务及索引变更均遵循统一规则 |

阶段 2、3 保留清锁流程不妨碍第一轮 workload 任务验收，但不能把它标成整个改造完成。SQL 现有更新路径提供实现参考；删除操作在提交时的物理清理、索引变更和共享读锁仍需单独处理，不能把整个 SQL 事务收尾替换成空函数。

## 代码组织与协作边界

| 位置 | 预计修改职责 |
|---|---|
| `core/dtx` | 共用记录操作、事务身份/状态接口、回滚记录、提交和回滚流程 |
| `core/base/data_item.h` | 记录事务引用与版本字段的解释；不直接把私有副本指针变成长期页内指针 |
| `compute_server` | 页面访问、远程记录更新、状态查询及提交协议衔接 |
| `core/storage` | 更新/撤销/事务终态的日志及恢复依据，保持 WAL 和回放可见性约束 |
| `workload` | 保留业务算法，改用显式记录操作 |

先在现有模块中抽取共用逻辑，不增加与旧 DTX 并行运行的另一套事务框架。实施时按上述阶段形成独立提交，双方通过本文件记录接口和语义的决定，再分开修改 workload 与内核调用点。

## 后续完整模型的服务器验证清单

使用现有四机环境和运行入口验证，不为缺少本地环境增加模拟测试框架。先用短事务与两个交互会话核对数据，再跑 Lazy、2PC 系列的同配置对照。

- 更新后提交、更新后回滚、同一记录多次更新、自读自写、后续语句失败时整笔回滚。
- T1 已更新尚未提交时，T2 的读取和写入遵守选定规则；T1 结束后，T2 能识别仍在页上的旧事务标记。
- 页面在事务结束前迁到其他计算节点，终态判定、继续写入和回滚仍正确。
- 提交时本地清理成功、因 latch 争用跳过、因权限转移跳过，都得到相同事务结果；延迟清理不能误清新持锁者。
- 多写参与者提交、远程操作重试、Prepare 后的结果查询，不重复安装更新或产生相反决议。
- 活跃/终态缓存缺失、节点重启后的事务身份和日志恢复：未实现恢复的阶段明确限制验证范围，不把正常路径通过当成恢复正确性。
- SQL 共享读锁、INSERT/DELETE 与索引变更按接入阶段分别验证，不用 YCSB 更新通过替代它们。

统计继续复用 `stats.log` 的主阶段、取页路线、日志等待和写参与者分组。只有现有指标无法回答具体问题时才补计时，不新增根目录专项测试脚本或重复统计表。

最终比较执行、提交、回滚和总耗时，并记录取页/RPC 次数、日志字节和实际刷盘调用。提交阶段变短本身不足以证明优化：需要排除仅把相同工作移到执行阶段，也要计入事务状态查询、延迟清理和失败撤销的成本。
