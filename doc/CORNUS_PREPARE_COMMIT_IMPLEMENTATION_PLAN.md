# WookongDB MP：基于持久化 Prepare 的提交优化实施方案

日期：2026-10-23  
状态：设计与实现交接文档；本文编写阶段未修改数据库代码。  
目标：实现 Cornus 思路下的正常提交路径，保留同步 Commit 执行，减少提交关键路径中的日志持久化等待。

## 1. 已确认的需求与边界

### 1.1 必须实现的行为

对于多个写参与者的事务：

1. 协调者完成业务计算，将最终写集按参与者划分。
2. 各参与者在 Prepare 阶段持久化自己的完整写集、事务元信息及 YES。
3. 协调者收到全部 YES 后确定提交，不再写入并等待原有 coordinator backup 决议日志。
4. 协调者仍然同步等待所有 Commit RPC 完成。
5. 参与者 Commit 正常更新页面、生成日志入队、释放或交接锁，然后返回；不再专门等待本次 Commit 结束日志持久化。
6. 协调者收到全部 Commit 完成回复后，才向调用方返回成功。

**本方案是日志持久化等待的优化，不是整个 Commit 过程异步化。不要打开 `AsyncCommit2pc` 来替代本方案。**

### 1.2 第一版覆盖范围

- `SYSTEM_MODE=2` 的多写参与者事务。
- `SYSTEM_MODE=4` 中选择 2PC 分支且有多个写参与者的事务。
- 优先覆盖当前 YCSB、SmallBank 的既有记录更新事务；不借此扩展 SQL、DDL、插入删除或任意业务操作的协议支持。

以下路径保留原语义：

- lazy 分支；mix 分流规则及热点阈值。
- 只读事务；零个写参与者的优化路径。
- 单写参与者路径，包括唯一写参与者在远端的情况。
- 页面迁移、推送、淘汰等路径的日志等待。
- 原有行锁、WAIT_DETECT 与锁交接机制。

### 1.3 明确不做

- `fdatasync` 失败、网络/RPC 失败的完整处理和重试框架。
- 实际故障恢复、节点接管、故障后的锁恢复。
- `LogOnce` / CAS 仲裁服务及超时终止协议的实际实现。
- 故障注入测试、288 组合实验、远程部署、性能实验矩阵。
- 完整 MVCC 或隔离级别改造、存储高可用改造。
- 在线日志垃圾回收、通用幂等服务或无限期保存完成事务的内存表。

正常路径假设 RPC 和存储持久化成功、节点正常运行。不得把这些假设包装为已实现容错。日志设计需要具备未来恢复所需的信息，但第一版不能宣称已经通过恢复验证。

## 2. 当前代码事实与需要特别注意的复用路径

实现前请再次阅读实际代码，函数名比本文件中的相对位置更可靠。

| 位置 | 当前行为 | 本次改造 |
|---|---|---|
| `core/dtx/dtx_exe.cc`，`Tx2PCCommit()` | 多写参与者走 Prepare、backup 刷盘、Commit | 构造准备写集，取消优化分支的 backup 日志及等待 |
| 同文件，`TxPrepare()` | 只向 `write_participants` 发事务 ID | 发送完整准备请求 |
| 同文件，`UniqueRWIndices()` 调用处 | Commit/Abort 按已取到的 tuple 去重 | Prepare 使用相同去重规则 |
| `compute_server/twopc_fetch_server.cc`，`Prepare_2pc()` | 等待 RPC 后直接返回 true | 正常响应必须真实汇总所有 YES |
| 同文件，`Commit_2pc()` | `sync=true` 会 Join 全部 RPC | 保留同步等待 |
| `compute_server/twopc_server.cc`，`Prepare()` | 写 `BatchEndLogRecord` 并等待 | 写完整准备记录并等待持久化 |
| 同文件，`Commit()` | 接收最终值、更新、日志入队、解锁、等待结束日志 | 新分支从准备上下文应用写集，省去末尾显式刷盘等待 |
| `core/storage/log_record.h` | 没有本方案的准备日志类型 | 追加新类型及编解码 |
| `core/storage/logreplay.cc` | UPDATE 会应用到页面；`restore()` 未实现 | 识别准备记录，但不将其当 UPDATE 应用 |

两个必须避免的误改：

1. `Tx2PCCommit()` 的单写参与者分支，如果唯一 writer 在远端，也会调用 `Tx2PCCommitAll()`，最终进入同一个参与者 `Commit()` handler。**不能无条件删除这个 handler 的刷盘等待。**
2. `Prepare` 记录不能借用现有 UPDATE 的普通应用逻辑，否则未决定提交的数据会提前进入存储页面。

当前工作区有用户未提交修改和实验产物。实现者应先查看 `git status`，只修改任务所需代码，不清理、不覆盖、不回滚已有改动。

## 3. 协议与路径选择

### 3.1 选择条件

仅当事务已经选择 2PC 执行路径，且 `write_participants.size() > 1` 时，使用新协议。

不要仅凭 `SYSTEM_MODE==2/4` 或“Commit 请求中只有本节点的记录”来决定跳过持久化等待；每个参与者收到的写集天然只属于自己，不能由此推断全局是否跨节点。

### 3.2 正常时序

```text
协调者                                  参与者 A/B/...
完成计算，生成 commit_ts
固定完整写参与者集合
构造去重后的最终写集
                 -- Prepare(元信息+本节点写集) -->
                                        检查锁归属和数据长度
                                        保存准备上下文
                                        写 PREPARED 日志
                                        等待该日志持久化
                 <-- YES ---------------------
收齐全部 YES：全局提交决定成立
不生成原有 backup 决议日志
                 -- CommitPrepared(事务标识) -->
                                        应用最终写集
                                        UPDATE/结束日志入队
                                        释放或交接锁
                                        不等本次结束日志刷盘
                 <-- Commit 完成 --------------
等待全部回复，返回事务成功
```

保留两个时点：全部 YES 持久化是提交判据；全部 Commit RPC 执行完成是用户成功响应时点。不得在第一版改为收齐 YES 就直接向用户返回。

### 3.3 明确区别普通 Commit 与已准备 Commit

建议在 RPC 中增加显式路径标记，例如：

```text
CommitKind:
    LEGACY = 0
    PREPARED = 1
```

- `LEGACY`：保留旧请求中的值及原有刷盘等待，尤其服务单个远程写参与者。
- `PREPARED`：要求存在匹配的已准备上下文，使用已持久化写集，不等 Commit 末尾日志刷盘。

也可新增独立 RPC 来表达同一语义；第一版优先采用修改更小、分支明确的方式。不要通过“查不到准备上下文就当普通事务”掩盖新协议错误。

协议变更后统一构建、更新 compute/storage 二进制，不要求新旧版本混跑兼容。

## 4. 数据结构与日志格式

### 4.1 事务唯一标识

新协议上下文和准备日志不能只按现有进程内自增 `tx_id` 建索引。建议单独使用复合标识：

```text
TxnIdentity = (coordinator_node, coordinator_incarnation, local_tx_id)
```

`coordinator_incarnation` 在进程启动时生成一次，可采用 128 位随机启动标识，避免依赖会重置的自增计数或仅秒级时间。第一版不新增持久化 epoch 分配服务；文档中明确其唯一性假设。保持原有 `tx_id/start_ts` 在既有锁、统计路径中的用途，不做全库 ID 重构。

### 4.2 Prepare 请求

建议包含：

- 协议版本与 `TxnIdentity`。
- `start_ts`：与现有写锁持有者身份对接。
- 已确定的 `commit_ts`。
- 完整、去重且排序稳定的写参与者集合，包括协调者自身（若其也是 writer）。
- 本参与者最终写集。

每个写项至少包含：`table_id`、页面/slot、必要的 key、操作类型、最终 value 字节。第一版操作类型可只支持既有 UPDATE；遇到不支持类型明确拒绝，不扩展实现范围。

持久化记录还需保存恢复时解析表所需的稳定信息：若表 ID 跨重启并非稳定，记录表名或可恢复的表标识映射，不能假设仅内存元信息足够。

最终值必须是拥有内存的字节串，不能把 `DataItem::value` 指针、页地址、互斥量、等待队列等进程内对象直接序列化。业务 after-image 与锁元数据分开设计；未来恢复不能用旧锁状态覆盖新的持有者。

### 4.3 `PreparedLogRecord`

建议在 `LogType` 尾部追加类型，保持已有枚举值不变。记录包含协议版本、事务标识、参与者集合、起止时间戳、本地写集、条目数、长度及完整性校验，完整记录即代表本参与者 YES。

使用显式字段编码；编解码检查长度及边界。可以复用 protobuf 消息作为日志 payload，外层仍遵循已有日志头格式，以降低重复实现成本。

第一版优先一个参与者一条完整逻辑准备记录：

- 完整记录持久化后才能回复 YES。
- 不完整记录不构成 YES。
- 如果单条记录可能超过现有 flush/replay 缓冲上限，必须增加明确的容量检查或分片结束语义，不能让 replay 永远等待一个放不进缓冲区的记录。
- 保留准备记录原始字节以支持未来恢复，不做自动日志裁剪。

### 4.4 LSN 与页面链条

准备记录进入现有节点日志队列，使用该日志流的 LSN 及既有 `wait_log_flush(prepare_lsn, ...)` 等待路径。

**不要为持久化准备写集而调用 `UpdatePageLLSN()`、修改页面内容、页面 `prev_lsn` 链或提前解锁。** 准备记录不是某次已应用的页面更新。

确认分配 LSN、入队顺序与现有互斥方式匹配，使等待该 LSN 足以覆盖完整准备数据。日志关闭时不能运行此优化并声称具备持久性；要求 `generate_log` 开启，使用清晰的启动/路径检查即可。

## 5. 协调者实施细节

### 5.1 提交前固定数据

在 `Tx2PCCommit()` 已生成 `commit_ts` 后、多参与者 Prepare 前：

1. 调用 `UniqueRWIndices()` 或等效已验证去重路径。
2. 基于 table/page/slot 组织写项，以当前事务最终 value 为准。
3. 按 `get_node_id_by_page_id()` 分组。
4. 验证分组节点集合与实际 `write_participants` 一致。
5. 固定事务标识和参与者集合，Prepare 后不再修改最终写集。

重复 key 的处理沿用原事务定义；不要在 Prepare 和 Commit 分别用不同规则选择同一 tuple 的最终值。

### 5.2 Prepare 汇总

并行发送所有请求，包括本节点 writer 对应请求；正常 RPC 结果逐一检查 `ok`/YES。修正当前“Join 后恒返回 true”的逻辑，不新增完整失败恢复系统。

RPC 超时/错误不作为本轮功能目标，但代码不能将错误算作 YES；可以沿用项目明确报错/断言方式。不得实现“超时直接回滚”并把它描述成 Cornus 恢复规则。

### 5.3 Commit 与统计

- 多参与者新分支移除 backup 日志生成及等待，不在提交前换一个名字再次刷同样的决议日志。
- 保留同步 `Commit_2pc(..., true)`，回调和请求生命周期覆盖全部 Join。
- 所有参与者执行完成后再运行既有 DTX 提交收尾、`FinishTx` 和成功计数。
- 保持只读、单写本地、单写远端分支。
- 沿用既有统计；新分支不再增加 backup 日志计数，相关阶段耗时不伪造为仍在执行。
- 不额外建设指标平台或修改已有实验结果。

## 6. 参与者实施细节

### 6.1 最小准备上下文

在 ComputeServer 或专用小型管理类内保存：

```text
PreparedTxnContext:
    identity
    start_ts, commit_ts
    participants
    owned write-set
    prepare_lsn
    state: PREPARING / PREPARED / APPLYING
```

使用受保护的 map；建议通过 shared ownership 取出上下文后再执行 I/O。不要拿着全局 map 锁等待刷盘、获取页面或执行 RPC，避免将所有事务串行化。

### 6.2 Prepare handler

- 检查协议版本、参与者集合、写项归属和长度。
- 按必要范围检查 tuple 的排他写锁属于该事务，允许该事务原有合法自持锁。
- mode 2 按原来的本地页面路径检查；mode 4 按现有 lazy 页路径检查。只短期持有操作页锁，不把页锁持有到整个 Prepare 刷盘等待结束。
- 拷贝最终写集到参与者拥有的上下文。
- 生成拥有独立 payload 的准备日志，放入已有日志队列。
- 等待准备日志持久化，置 PREPARED，回复 YES。
- 此阶段不应用业务新值、不释放事务行写锁。

正常接口若被重复调用，应至少识别同一事务身份，禁止用不同写集覆盖已准备状态。无需实现跨重启通用去重，但不能默默生成两份不同的 YES。

### 6.3 Prepared Commit handler

- 根据明确的新路径标记和事务标识找到 PREPARED 上下文。
- 验证事务/提交时间戳一致；缺失上下文是实现错误，不假装成功。
- 按当前 mode 2 / mode 4 获取页面的方式执行，复用已有 UPDATE 日志生成及页 LSN 维护。
- 保持写入业务值、生成拥有副本的日志、释放页面操作锁、交接行锁之间的正确发布顺序。修改行锁字段时仍必须持有相应页面保护；不得为了异步日志改变现有对其他线程可见的顺序。
- 保留 `UnlockTupleWithHandoff2PC`、`DeliverHandoff2PC` 和必要的 `FinishTx`；避免新增一次重复 FinishTx/解锁。
- UPDATE 日志、结束记录仍然进入后台日志队列，队列拥有记录及其 payload。
- 新分支跳过 handler 末尾专门等待本次结束日志的 `wait_log_flush`，然后返回 Commit 完成。
- 确保所有日志已复制写集后释放上下文，避免每事务永久占用内存。

### 6.4 普通 Commit handler

`LEGACY` 分支保留旧请求和刷盘语义，包括单写参与者在远端的路径。分支行为必须可从代码明确辨认。

## 7. 日志回放、页面一致性与关闭流程

### 7.1 在线 replay 的必要适配

在日志读取分发中加入新类型的反序列化，在应用路径中识别为准备元数据：

- 不修改业务页面、bitmap、索引和页面 LSN。
- 正常消耗该条日志字节，更新正确的日志读取进度，不能卡住其后的 UPDATE/LOCK/BATCHEND。
- 不把单个参与者 PREPARED 当作全局事务 COMMIT。
- 第一版无需建立持久化投票索引或恢复扫描器；磁盘记录保留完整信息，未来可扫描。说明 replay 进度不等于准备记录可被删除。

不要直接在函数开头 return 而跳过原函数负责维护的 offset 等公共收尾逻辑。检查现有 `apply_single_log` 中的前置路由和 LSN 逻辑，确保它不会把新类型误当作页面日志。

### 7.2 保留正常页机制

继续使用当前 mode 2 的 local page 路径、mode 4 的 lazy page 路径。保留推页、淘汰和 GetPageWithLsn 等一致性等待。

Prepared Commit 可能在获取或释放页面时因既有机制间接等待日志；不能为了制造“零 Commit 等待”指标而绕开这些步骤。

### 7.3 正常退出

事务日志异步持久化后，更需要保留正常结束时已有的日志 drain/最终 flush 顺序。确认在停止存储服务前，计算节点已完成 Commit RPC 并排空相关日志。只修正本改动引入的遗漏，不扩展为通用关闭/容错框架。

### 7.4 本方案不修复的已有问题

保持当前锁和读路径并不等于证明完整可串行化或完成 MVCC。本方案只保证不新增“成功回复先于所有参与者页面更新完成”的窗口，不声称解决现有并发隔离问题。

## 8. 理论恢复约定：设计保留，实现延期

### 8.1 提交规则

- 所有写参与者都有完整持久化 YES：事务必须提交，用户是否收到成功不改变结果。
- 存在合法确定的 ABORT：事务回滚。
- 只有部分 YES：不能提交；未来恢复通过原子封闭尚未投票的位置来确定回滚。
- 存储不可访问：结果未知，不能任意判定。

### 8.2 为什么不能只查询缺失记录就回滚

三个参与者 A、B、C：A/B 已 YES，恢复线程查到 C 的位置为空；若线程直接宣布回滚，而 C 同时写入 YES，就会出现部分节点已回滚、日志却有三个 YES 的矛盾。

未来的 `LogOnce` 对 `(事务身份, 参与者)` 的投票位置做原子写入：

- ABORT 先占据空位，迟到 YES 不能再成功。
- YES 先占据空位，代写 ABORT 返回已有 YES；若全员 YES，则提交。

第一版不实现这项 API，不模拟一个普通 map 并宣称具有持久化 CAS/恢复语义。YES 投票与最终应用完成状态是不同概念，未来的状态机不得将投出 YES 的参与者直接以本地超时回滚。

### 8.3 为什么日志信息足以支撑后续实现

准备记录提供全局身份、完整参与者集合、各方最终写集及提交时间戳，因此未来恢复程序可以确定决议并补齐更新。尚需实现的部分包括投票仲裁、重复应用判定、页面顺序恢复、锁与缓存重建以及安全日志回收。

这说明的是恢复设计所需证据已预留，不能据此称本版已支持崩溃恢复。

## 9. 分步实施与交付检查

### 9.1 实施顺序

1. 读实际代码和工作区状态，标记上述共享 handler 与单写远端分支。
2. 定义新协议标识、事务身份、Prepare payload、准备日志编码。
3. 适配日志解析和在线 replay，使新记录不会提前应用或堵塞回放。
4. 实现参与者上下文与持久化 Prepare。
5. 修改协调者构造最终写集、汇总 YES、发送 Prepared Commit。
6. 先连通同步执行流程，再移除优化分支的 backup 日志及 Commit 末尾等待。
7. 确认 mode 2 与 mix 的路径都正确，原有只读/单写/lazy 分支保留。
8. 检查正常退出的日志排空，编译并报告结果。

不创建新的 SYSTEM_MODE，不改变 mix 阈值，不顺手修改工作负载和实验脚本。若实现确实需要额外开关，应先说明必要性，避免无目的增加配置。

### 9.2 构建注意事项

- 修改 `.proto` 后由项目使用的 protoc 生成 `.pb.h/.pb.cc`；不要手写生成文件。
- 顶层 CMake 当前会在配置阶段重新生成多个 proto。审查 diff，避免提交无关版本漂移；不要覆盖已有用户改动。
- 依赖与环境参考 `doc/build_env.md`。文档描述的是 Ubuntu 构建环境，不保证当前执行机器已有同样依赖。
- 只运行正常编译和必要的现有轻量校验；不新增故障测试，不自动连接远端集群或启动长实验。
- 若无可运行环境，准确报告未验证内容，不用“应当能跑”替代实际结果。

### 9.3 最小静态验收清单

- [ ] 新路径只作用于多写参与者的 2PC 事务。
- [ ] 参与者 YES 之前完整写集已持久化；所有节点共享同一身份、参与者集合、commit_ts。
- [ ] 准备日志没有改变业务页或页面 LSN。
- [ ] 新日志能被解析并推进回放进度，不误触发业务更新。
- [ ] 优化路径不再生成或等待 coordinator backup 决议日志。
- [ ] Prepared Commit 正常应用写集、日志入队、锁交接，然后回复；末尾不等 Commit 日志。
- [ ] 协调者仍等待全部 Commit RPC，之后才返回成功、更新成功统计。
- [ ] 单写本地与单写远端保留原有持久化等待，尤其没有被共享 handler 误伤。
- [ ] lazy、页面迁移、淘汰和普通 Abort 的原有行为未被无关修改。
- [ ] map 锁不覆盖刷盘/RPC；日志 payload 独立拥有内存；事务结束后上下文释放。
- [ ] 正常退出保留日志排空，统计不把后台工作消失误说成开销消失。
- [ ] 没有声称实现 LogOnce、故障恢复或经过故障测试。

这份清单用于代码审阅和实现自检，不是要求本轮新增整套测试系统或运行实验矩阵。

## 10. 性能解释与后续工作

第一版减少的是 coordinator 决议与参与者 Commit 的显式持久化等待，保留 Prepare 的持久化、Commit RPC、页面获取和锁交接成本。后台日志最终仍需落盘，不能说系统不再需要 fdatasync。

Prepare 会增加写集传输与日志大小。为复用现有回放，第一版允许准备日志和后续 UPDATE 日志重复包含最终值。吞吐收益必须以后通过实验测量，不能根据删去等待直接承诺性能提升。

后续独立任务可包括：完整 LogOnce/恢复实现、日志去重与回收、故障测试、性能实验，以及基于新 2PC 成本重新设计 mix 分流模型。本次不顺带实现。

参考论文：[Cornus: Atomic Commit for a Cloud DBMS with Storage Disaggregation, PVLDB 16(2), 2022](https://www.vldb.org/pvldb/vol16/p379-guo.pdf)，重点阅读 §3.2–3.4。本文保留同步 Commit 完成后才回复用户，是为当前原型收窄范围后的实现选择，不等同于论文全部流程。
