# YCSB 页面时间局部性：worker 私有 LRU

> 历史实验记录：后续按讨论改为 YCSB/SmallBank 共用的 ID 复用，当前代码已移除下文的页面复用参数。本文保留页面实验的定义与结果；复现旧版应使用归档源码补丁。当前实现见 [ID 复用实验](ID_REUSE_EXPERIMENT_20261117.md)。64 个 ID 与 64 页不是等价窗口。

本轮实现讨论确定的页面近期窗口，只改 YCSB 负载生成及参数读取，不改变事务执行、锁、快照读、日志或提交协议。页面版本测试时使用未提交代码，通过同步工作区补丁部署。本次仅将其历史实验记录与后续 ID 复用实现一起收录，页面版源码保留在结果归档。

## 参数和范围

`config/ycsb_config.json` 的 `ycsb` 中新增：

```json
"page_reuse_prob": 0.0,
"page_reuse_window_pages": 64
```

- `page_reuse_prob`：从近期页面选择的概率，范围 0–1。0 默认关闭，不增加原生成流程的随机数消费；支持整数 0/1 或小数。
- `page_reuse_window_pages`：每个 worker 窗口可容纳的不同页面数，开启时必须为正。不是缓存容量，不是最近多少次访问或多少秒。
- 复用功能接入本轮使用的 YCSB Zipf 分支（`use_zipfian=1`）。关闭时原有生成模式均保留；开启但选择其他生成模式会明确报错，不悄悄忽略参数。没有改 SmallBank/TPC-C。
- 默认配置保持关闭。实验仅扫描概率，窗口容量固定为 64 页。

## 生成与维护规则

1. 每个 `RunYCSB` worker 持有一个 `PageReuseWindow`，与其 Zipf 状态一样独立。共享的 YCSB 对象只保存配置，不保存可变窗口。
2. 首先按已有规则决定本次操作的读写类型和固定数据归属节点；`local_ratio` 与 `write_owner_count` 的规则不变。
3. 复用分支只考虑旧窗口中归属匹配的页面，均匀选页，再均匀选页内记录。使用实际 RID 和已有节点 key 列表，不用 key 算术反推页面，因此适配现有随机 key 布局。
4. 窗口为空或没有合适候选时，回退到原 Zipf 分支。固定写者模式原有的事务内 key 去重要求保留：若候选页内所有记录已经使用，移出本次候选列表，继续选择；候选耗尽再回退，避免无限重试。
5. 生成整笔事务的十个目标期间，窗口不变。不把刚为本笔事务新选中的页立即用于复用采样。
6. 全部目标生成后，按生成顺序更新 LRU：已有页移到尾部，新页加入尾部，满时淘汰头部。同页只保留一项。读写共用窗口，不区分页面类型。
7. 窗口依据生成的逻辑目标更新，之后事务是否访问完、回滚或提交均不影响该更新。它不查询实际 BufferPool、权限或当前物理持有节点，不替 Lazy 挑缓存命中页。
8. 复用选择使用 worker 种子派生的独立随机状态，不消费原归属选择的随机流。两种模式按相同 worker 的生成尝试前缀使用相同规则；时间模式下完成数量不同，不声称整个运行访问了完全相同数量的请求。

所有页面都有机会进入窗口，但每个 worker 当前只保留一小部分。LRU 命中会延续页面的活跃性；这是最近不同页面集合，不保证固定秒数后过期。概率 1 可能在候选充足时长期维持小工作集，不等价于自动轮换热点。

`page_reuse_prob` 不是实际复用率，更不是缓存命中率。基础采样也可能自然重访；窗口分支可能回退；已有页还可能被其他节点拿走或淘汰。最终分布是 Zipf 基础采样与近期页采样的混合，不再是原来的纯 Zipf，冲突和页内空间局部性也可能变化。

## 代码入口

- `compute_server/worker/handler.cc`：读取参数，传入 YCSB 配置。
- `compute_server/worker/worker.cc::RunYCSB`：创建 worker 私有窗口并跨事务保留。
- `workload/ycsb/ycsb_db.h::generate_ten_keys`：旧窗口候选筛选、页内记录选择与事务生成后的 LRU 更新。
- 页面首尾 key 范围来自按页面分组的 `GetNodeKeys` 和 `MetaManager::Fetchrid`，只查询已有元数据，不额外发取页 RPC。

## 服务器验证与实验计划

基线 HEAD 为 `09fed8e` 加本轮未提交补丁，不能将 HEAD 单独当成测试版本。四台部署仓库同步代码补丁，在服务器编译；本地不编译或运行模拟负载。结果保存 source fingerprint、配置与补丁快照。

先验证默认关闭，以及窗口 1 页、概率 1、固定单写归属的真实集群短测，Lazy/Cornus 各 5 秒。后者检查候选不足和固定写集合记录去重的回退路径。首次默认短测发现整数概率与旧 JSON 浮点读取接口不兼容，已只修复新参数读取；失败记录保留，不纳入性能结果。

正式对照固定：三计算节点、每节点 2 worker、RDMA、YCSB 4 读 6 写、θ=0.6、NO_WAIT、每表数据缓存 10,000 页、buffered 读取、日志开启、现有 `-O0 -DDEBUG` 构建。存储节点沿用用户之前的云盘配置，本轮未通过云 API 独立核验 IOPS 配额。

`write_owner_count=3` 固定写归属，避免复用概率变化引起单写/多写路径比例变化；因此本轮保留的 `local_ratio=0.5` 不控制目标放置。每点 30 秒，概率 0/0.5/0.9，Lazy 与 Cornus；第二轮反转概率和模式顺序，共 12 次正式执行。

复用既可能减少跨节点取页，也可能减少存储缺页。沿用已有路径计数和耗时分开观察，不把两者都称为计算节点 RPC。窗口维护自身的生成开销包含在事务总时间与 TPS 中；主 execute 计时不完整覆盖负载生成，因此还检查未归属阶段的时间。

正式结果的源码指纹统一为 `ef3761a24187a3890997edb7c95a7cb465da9d1de6b6c66250d38a8b6f4c59a3`；HEAD 仍为 `09fed8e`。功能短测验证的是实际运行、断言及统计对账，不是完整故障恢复或业务数据不变量审计。

### 获取次数与单次耗时

两轮计数、累计时间先合并再归一化。分母是完成尝试，包含回滚。Lazy 跨节点相关取页采用 `local_manager + owner_manager + forwarded_page + wait_release`；存储取页、权限升级另列。它是逻辑获页过程，不是网络报文个数；一次过程可能有多次通信。Cornus 采用成功与冲突回复合计的 GetDataItem RPC。

|---|---|---|---|---|---|---|
| 0 | 5.896 | 0.1500 | 0.885 | 6.656 | 0.0942 | 0.627 |

双方存储获取和淘汰均减少，说明这个负载同时改善了缓存局部性。概率 0.9 时，30 秒运行内没有观察到淘汰；这个结论受运行长度和工作集增长速度影响，不能直接外推为长期永不淘汰。统计包含初始冷缓存阶段。

### 完整执行、提交与吞吐

TPS 展示两轮观测范围，不是置信区间。执行和提交按累计完成尝试归一化。

| 复用概率 | 模式 | Commit TPS 范围 | 执行 ms/尝试 | 提交 ms/尝试 | 回滚率 % |
|---|---|---|---|---|---|
| 0 | Lazy | 2290–2337 | 1.230 | 1.328 | 0.39 |
| 0 | Cornus | 2121–2144 | 0.753 | 2.007 | 0.78 |
| 0.5 | Lazy | 2729–2734 | 0.735 | 1.398 | 0.32 |
| 0.5 | Cornus | 2127–2139 | 0.729 | 2.000 | 0.72 |
| 0.9 | Lazy | 2967–2990 | 0.296 | 1.658 | 0.21 |
| 0.9 | Cornus | 2149–2172 | 0.695 | 1.998 | 0.63 |

同轮配对，Lazy 相对 Cornus 的吞吐优势从概率 0 的 6.8%–10.2%，扩大到 0.5 的 27.6%–28.6%，再到 0.9 的 36.6%–39.2%。概率 0.5 时双方执行接近，0.9 时 Lazy 执行更快。复用收益没有被额外提交开销完全抵消，但 Lazy 提交等待由 1.328 增至 1.658 ms，因此不能只依据执行阶段下降估计最终收益。

窗口相关生成工作包含在事务总时间和实际 TPS 中。`total - begin - execute - commit - abort` 的未归属时间，Lazy 从约 0.014 增至 0.046 ms/尝试，Cornus 从约 0.013 增至 0.051 ms/尝试。这还包含其他负载准备工作，不是对 LRU 代码的独立计时；不能将它重复加入完整事务时间。

设备 TPS 窗口交集内，各 case 写 IOPS 均值约 8,242–9,170，读 IOPS 均值最高约 0.71。存储 RPC 不等于物理设备读；这里也不据客户机计数推断云端限流状态。

## 本轮能说明什么

固定节点归属分布和写参与者数量后，通过近期页面窗口增加访问时间局部性，Lazy 可以让后续访问更多地在本地完成；owner-side 路径仍需逐次 remote fetch。本轮因而支持“搬来后继续利用页面”能够改变双方执行优势的判断。

这仍是一个受控原型负载：近期窗口改变了实际访问分布、页内访问和竞争，不能把 TPS 增量全归给单个计数，也没有将跨事务复用和事务内同页访问的贡献精确拆开。下文补充每节点 8 worker；尚未评价不同窗口容量、长时间运行或真实业务追踪。没有推进新 MIX 策略。

## 补充：每节点 8 worker

### 为什么吞吐没有随 worker 增长四倍

每个 worker 同时执行一笔事务，下一笔要等这一笔完成。无复用 Lazy 的完整尝试平均时间由约 2.6 ms 增至 3.263 ms，Cornus 为 3.349 ms；高复用 Lazy 为 2.321 ms，Cornus 为 3.398 ms。以 24 个并发尝试估算，`24 × 提交比例 / 平均尝试秒数` 与实际 TPS 接近。因此两三千 TPS 的前一轮首先是低并发下的闭环结果，并非已测得系统峰值；这轮增加并发后，等待和冲突也有所增加。

按各节点 TPS 时间窗的交集、首尾各留 2 秒对齐 `mpstat`/`iostat`，每点取到 24 个一秒样本：

- 计算节点 CPU 忙碌比例（`100 - idle - iowait - steal`）约 19%–40%。Lazy 三种概率的跨节点/两轮均值分别约 39.2%、32.8%、19.4%；Cornus 约 28%–29%。未见整体 CPU 饱和；平均利用率不能排除局部串行瓶颈。
- 存储节点 CPU 忙碌约 12%–14%，iowait 约 24%–28%；设备写 IOPS 各点均值约 8,011–9,207，采样窗口内读 IOPS 均为 0。不能根据客户机计数确认或否认云端限流，也不能把 RPC 读次数当成物理读 IOPS。
- 平均单次 `fdatasync` 为 0.736–0.839 ms，但事务提交时间是 1.549–2.467 ms，包含其他等待和协议工作，二者并不相等。高复用 Lazy 的提交时间占完整尝试约 73%，Cornus 约 73%；继续减少执行访问也会遇到提交等待的限制。
- Lazy 的 `fdatasync/commit` 随概率为 0.395、0.327、0.276，Cornus 约 0.396–0.399；WAL 约 14.7 与 14.3–14.4 KiB/commit。相比 2 worker，每次提交摊销的同步调用减少，说明更多并发允许更充分合批。TPS 增加不要求设备 IOPS 同比例增加；`fdatasync` 次数也不等于块设备 IO 次数。

上述证据支持当前吞吐受到同步等待与有限在途事务数量约束，尚不能把绝对性能归结为 CPU 或 2 万 IOPS 配额。构建仍是根 CMakeLists 强制的 `-O0 -DDEBUG`，优化构建的影响本轮没有测量；设置 Release 也不能直接视为已经消除这两个显式选项。
