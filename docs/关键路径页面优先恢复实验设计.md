## 1. 研究问题与建议结论

### 1.1 要解决的不是“索引页总比数据页重要”

一个数据页已经恢复，但某条访问它的查找路径上仍有索引页不可用，该查询依然不能完成。反过来，索引路径已经恢复、目标数据页未恢复，也会造成等待。

因此，调度目标应该是：

> 在最后的大批量回放前，用有限的识别与优先回放预算，先补齐最有价值的查询路径，让实际查询更早完成，而不是单纯让更多页面更早显示为“已恢复”。

这里的“数据页不能服务”特指依赖该索引路径的查询；不能据此阻止合法的顺序扫描、其他已就绪访问路径使用该数据页。

### 1.2 推荐方法

不建议在故障后遍历全树、扫描全库，求一个精确的“关键页全集”。识别工作本身很可能比优先恢复省下的时间还长。

建议采用四层信息，按成本递增使用：

1. **已有页状态与页面角色**：利用 IR 列表、存活副本报告、已知根页/内部页信息，快速缩小候选集。
2. **真实阻塞请求**：请求首次遇到不可用页时，报告当前阻塞页，形成实时需求。
3. **低比例访问路径采样**：正常运行时顺路记录少量“索引路径—数据页”关联，提前看到尚未暴露的下游依赖。
4. **预算内的非阻塞探测**：只对少量高收益候选补充信息，遇到未就绪页立即停止，不为识别完整路径遍历全树。

调度时既考虑单个页面，也考虑能完成一个查询的“小恢复组”。识别预算或优先回放预算耗尽后，立即进入原有批量恢复，不能无限等待更精确的决策。

### 1.3 建议验证的三个假设

- **H1：需求比页面类型更重要。** 实际等待请求和访问路径，能比“全部索引页优先”更有效地缩短查询恢复时间。
- **H2：少量关联信息已足够。** 低比例采样配合实时阻塞反馈，可能接近全信息参考策略，而正常运行与故障后的识别开销明显更低。
- **H3：需要主动停止识别。** 在恢复积压很小、访问均匀或路径信息严重过期时，继续搜索关键页可能得不偿失；有预算和降级机制的策略应当减少这种损失。

这些是假设，不预设所有场景都能加速，也不宣称算法具有全局最优性。

## 2. 当前实现提供了什么，哪些条件尚不成立

### 2.1 可以复用的部分

- `compute_server/server.h` 中的 `MarkNodeFailed()`：清理故障节点状态、GPLM 接管、LPLM 扫描及恢复调度入口。
- `RunIRRecoveryScan()`：收集存活节点的页面持有状态，可以附带有界的候选摘要。
- `RunIRRecoveryPhase3()`：将剩余 IR 页按每批 500 页发给存储层。
- `core/storage/storage_rpc.cc` 中的 `AnalyzeRecoveryPages()`：现有存储恢复入口。
- `core/storage/logreplay.cc` 中的 `RedoForPages()`：heap 页日志分桶和应用逻辑。
- `core/storage/undo_area.cc`：已有事务 Undo 链。
- `core/index/bp_tree/blink/blink.cc`：可以在已有索引查找过程中采集实际路径，而不用为采样另走一遍树。

### 2.2 四个会直接影响实验结论的约束

#### 约束一：现有流程先等待后台回放追平

```521:524:Hybrid_Cloud_MP/core/storage/storage_rpc.cc

                lr->WaitReplayCaughtUp();
                lr->PauseReplay();

```

如果全部物化工作已经在这个等待期间完成，之后再调整 `RedoForPages()` 顺序，可能只改变检查、解锁或取页顺序，不能证明“关键索引页提前回放”的收益。

**真正的回放优先级实验必须把调度器接到可调度的物化任务之前，并区分日志分析与物理应用。** 不能简单删除等待而忽略并发正确性。

#### 约束二：现有定向 Redo 不支持任意索引物理页

因此，“找到关键索引页”和“可以安全、独立回放这个索引页”是两个问题。后者需要公共恢复底座，不能在评估选择算法时假装已经存在。

#### 约束三：只重排请求数组不一定改变实际回放顺序

`RedoForPages()` 用按表名、页号排序的 `std::map` 收集页面，随后遍历该映射执行恢复：

需要显式维护存储侧的执行队列，而不是只对计算端的 `remaining_pages` 或 RPC 数组排序。结果下标与执行顺序可以分离。

另外，当前结果在整个 RPC 完成后才处理。若优先页先执行但仍等 500 页全部完成才解锁，早执行未必变成早服务。实验需要相同的微批次发布机制或完成通知机制。

#### 约束四：当前提交、Undo、失败解锁语义不能直接支持任意提前开放

- `UndoAllActiveTxns()` 遍历全部活跃事务链，并非仅故障节点事务。
- `ReportPageStatus()` 的现有处理不能作为可靠的“副本已验证”证明。
- 现有恢复 RPC 失败后存在直接解除 IR 的路径。
- `AnalyzeRecoveryPages()` 的部分 `page_data` 在 Undo 前生成，不能直接作为最终可见页面。

本文要求所有主对照策略使用相同、可靠的就绪条件。不能用少做 Undo、超时即放行、读旧缓存来换取表面上的恢复加速。

### 2.3 两种实验结论必须分开

| 实验实际做了什么 | 可以得出的结论 |
|---|---|
| 调整管理权接续、IR 解锁和存活副本使用顺序 | 页面可用性调度效果 |
| 在真实未完成的物化任务上改变索引/数据回放顺序，并提前提供正确查询 | 日志回放优先级的端到端效果 |
| 只在轨迹上模拟恢复耗时 | 选择算法在该模型下的潜力，不是数据库实测加速 |

## 3. 页面分类：先排除不需要回放的对象

以下分类同时用于数据页、索引叶页和索引内部页。“管理者”指 GPLM 管理者，不等于最新副本持有者。

| 类别 | A 故障前的情况 | 优先采取的动作 | 是否必然需要 Redo |
|---|---|---|---|
| P0 | B/C 管理，A 不持有页面，也无相关未完成传输 | 正常使用 | 否 |
| P1 | A 从 B/C 借 S 权限 | 清除 A 的共享持有记录，核验有效来源 | 否 |
| P2 | A 从 B/C 借 X 权限 | 隔离，核验基线和日志，必要时恢复最新内容 | 可能 |
| P3 | B/C 从 A 借 S 权限 | 核验副本，重建管理关系 | 通常不是内容 Redo |
| P4 | B/C 从 A 借 X 权限 | 确认有效持有者并接续管理关系 | 通常不是内容 Redo |
| P5 | A 管理，没有可验证的存活副本 | 核验存储版本，必要时日志恢复 | 可能 |
| P6 | 锁升级、授权、推页尚未完成 | 先确认状态；不能把 granting 当完整副本 | 待确认 |

分类只说明页面级故障影响；待撤销事务、迟到 RPC、结构修改还可能使页面不能发布。

识别候选时只纳入**确实未就绪且有可执行恢复动作**的对象。对已经就绪的根页打再高分也没有作用；有可靠存活副本时，应先选择便宜的核验/接续，而不是无条件重放日志。

## 4. 什么是“关键页面”

### 4.1 以查询依赖定义，而不是以树高度定义

设查询 \(q\) 的合法访问路径需要一组恢复单元 \(D(q)\)。恢复单元通常是一个页面；遇到树分裂等情况，也可能是一个不能随意拆分的结构修改组。

\(D(q)\) 包括：

- 实际需要的索引入口、内部页、叶页及右链修正路径；
- 命中时的目标 heap 页；
- 必须共同满足的结构恢复、事务结局和可见性条件。

设时刻 \(t\) 已合法就绪的单元集合为 \(A_t\)，则剩余依赖为：

\[
M_t(q)=D(q)\setminus A_t
\]

- \(M_t(q)=\varnothing\)：不再因恢复依赖而阻塞，仍需服从正常事务锁。
- \(|M_t(q)|=1\)：这个单元是该查询的“最后一个恢复阻塞点”，优先处理往往能立刻产生收益。
- \(|M_t(q)|>1\)：只恢复一个页未必能完成查询，需要考虑小组协同。
- 路径不完整：只能认定已观测到的“当前阻塞点”，不能冒充最后一个阻塞点。

### 4.2 必须处理的几个特殊情况

1. **同一 heap 页可能对应多个叶页。** 不建立无条件的一对一“数据页—索引页”映射，按键或查询路径记录关联。
2. **共享根页不是全表恢复屏障。** 多条路径共享根页时，根页只恢复一次，不把所有后代数据页合并成一个巨型恢复组。
3. **`key2leaf` 会改变实际路径。** 命中后可能直接访问叶页；不能假设每个查询都经过根页。需要记录实际缓存命中与回退路径。
4. **索引未命中没有目标数据页。** 只有相关键范围已完整、可信，才能返回 NOT_FOUND；未恢复不能伪装成不存在。
5. **物理页号与结构版本相关。** 旧路径是调度提示，不是正确性依据。结构变更后失效或重新验证。
6. **事务可能还受其他因素阻塞。** 页面恢复就绪不等于整个事务立即提交，测量时应分开记录锁等待、恢复等待与事务终结时间。

## 5. 关键页识别方法

### 5.1 方法 A：已有元信息与静态结构先验

利用已有 IR 集合、页面类别、可信副本、已缓存的页角色信息，形成低成本候选。

可用先验包括：

- 当前存在请求等待的页；
- 已知的索引文件头、根页、内部页；
- 数据已就绪、索引尚缺一段的路径；
- 有便宜存活副本来源的页面。

不能为获得页层级而扫描所有索引页。没有现成角色信息时标为未知，后续在正常取页中补全。

该方法作为低成本基线。它容易遗漏热点叶页，也容易高估被 `key2leaf` 绕过的根页价值。

### 5.2 方法 B：首次阻塞报告——最先实现

在取页入口和 IR 等待入口记录：

- `recovery_id`、`request_id`、`lookup_id`；
- 当前 `page_ref` 和页面类别；
- 首次阻塞时刻、请求开始时刻；
- 查询类型、必要的逻辑键标识；
- 已观测到的路径前缀。

每个请求在同一恢复代、同一阻塞页上只登记一次。页面就绪、请求取消、事务重试或阻塞点变化时更新登记。

**不能把 1ms 的 IR 轮询次数当成需求量。** 等待越久的一个请求不应被算成几千个请求。等待年龄可以作为单独的权重。

优点：

- 信息来自真实需求，额外工作主要是有界计数、摘要和通知，不需要额外走树。
- 对故障后的热点迁移敏感。

局限：

- 只能先看到路径上第一个阻塞页，下游可能尚未暴露。
- 所有工作线程卡在根页时，根页下面的需求不可见。
- 本地锁等待和缓存命中也可能绕开远程 RPC，埋点不能只放在服务端 GPLM。

对应措施：利用方法 C 的历史路径补充；对已到达但尚未执行的前台请求，可在请求接纳层做有界摘要。未到达的未来请求不能被在线算法提前读取。

### 5.3 方法 C：正常查找时采样路径——推荐与 B 组合

在已有 BLink 查找中以请求为单位随机采样，记录：

| 字段 | 含义 |
|---|---|
| `table_ref`、`key_tag` | 表及键标识；测试数据可直接记录键，线上可用摘要 |
| `path` | 实际访问的文件头/内部页/叶页/右链页 |
| `data_page` | 命中时的 heap 页；未命中为空 |
| `generation` | 用于判断路径提示是否过期 |
| `last_seen`、`sample_weight` | 时间衰减和采样权重 |
| `lookup_mode` | 直接叶页缓存命中、根查找或回退 |

实现原则：

- 抽样按请求独立决定，不只采样某些固定键，否则可能漏掉整片热点。
- 采样只复用已经发生的访问，不额外取页、不额外获取树锁。
- 每线程先缓冲，再批量合并；避免每次索引访问争用一个全局追踪锁。
- 用固定容量和时间窗口限制内存；允许丢提示，不允许因为提示缺失错误放行。
- 初期仅使用 B/C 留存的摘要。A 的内存追踪会随故障丢失，不能在在线算法中免费使用。
- 若增加摘要复制，复制的 CPU、内存、网络和正常吞吐代价必须单独计入。

故障后把路径与未就绪集合求交，得到候选剩余依赖。针对已经就绪的数据页，可以通过采样反向关联找到仍缺失的索引部分，避免从所有 heap 页重新提取键。

历史权重采用时间衰减，并结合故障后实时需求修正。实时等待请求和历史预测需求要去重，不能将同一批请求重复计分。

**完整性标记不可省略：** 路径版本不匹配、截断、只见到前缀时，标记为不完整，降低置信度，不能使用“最后一个阻塞点”规则。

### 5.4 方法 D：预算内非阻塞探测——可选增强

只对排名靠前、但信息不足的少量候选做补充探测：

1. 优先查询内存中的页面状态目录和路径摘要。
2. 必要时沿已经合法就绪的索引页向下一层推进。
3. 遇到首个未就绪页、版本冲突或预算耗尽，立即返回未知/当前阻塞点。
4. 不等待不可用页恢复后才结束一次“识别”，不递归扫描整个子树。
5. 探测未获得完整路径时，可将该阻塞页作为有界探索候选。

如果为了看到下一层而真的恢复了一个页面，这部分开销属于**探索性恢复**，要计入优先回放预算和总 I/O，不能记作免费的信息获取。

实际探测可能改变缓存状态。应记录新增页读取量、缓存命中变化，并设置“执行同样探测但不重排”的对照，区分信息价值与预热收益。

### 5.5 推荐组合

第一版选择 **B＋C**：实时首次阻塞反馈，加 1% 请求路径采样。

A 作为冷启动和信息缺失时的回退；D 作为独立可开关增强项。先证明 D 的净收益，再考虑默认开启。

## 6. 如何选：从单页热点到“可完成查询的小组”

### 6.1 候选单元和安全依赖闭包

调度器接收公共恢复底座给出的合法单元：

- 可独立恢复的 heap 页；
- 可独立恢复的索引页或固定键域；
- 必须共同恢复的结构修改组；
- 必要的前驱、元数据和事务处理任务。

对候选组先补齐必需依赖，得到合法恢复组 \(G\)，再估价。共享依赖只计算一次。

同 key 操作顺序、页日志前驱及结构修改顺序不能为了优先级被打乱。候选过大或跨越尚不支持的结构操作时，退回公共批量恢复。

### 6.2 两步选择，避免全图搜索

**第一步：粗排。**

对有限候选维护实际等待量、等待年龄、预测访问量和恢复成本，选出 Top-K。候选来源是增量事件和有界摘要，不是每次重扫全部 IR 页。

**第二步：精排。**

只为 Top-K 构造：

- 单个有实际等待的恢复单元；
- 完整路径上剩余依赖形成的小恢复组；
- 少量高重叠候选的合并组。

不枚举任意页集合。把索引根、叶页、数据页连接为“查询依赖”，而不是将整个连通图视作一个必须同时完成的任务。

### 6.3 一个可实现的启发式评分

对候选组 \(G\)，采用：

\[
\operatorname{Score}(G)=
\frac{
\sum_{q:\,\varnothing\ne M_t(q)\subseteq G} w_q\pi_q
+
\alpha\sum_{q\in F(G)}w_q\pi_q
}{
\widehat C_{exec}(G)+\widehat C_{extra\_id}(G)+\varepsilon
}
\]

其中：

- 第一项：有足够信息确认，完成该组即可消除恢复阻塞的查询权重。
- \(w_q\)：请求权重。初版同权，之后可加入有上限的等待年龄，避免长期饥饿。
- \(\pi_q\)：路径和需求预测的置信度。真实已验证信息与过期提示应区别对待。
- \(F(G)\)：只能确认当前阻塞点位于该组、但下游未知的请求；与第一项不重复。
- \(\alpha\)：探索权重。初值可设 0.1，并与 0、0.3 做消融；探索进展不能在结果中算作查询已完成。
- \(\widehat C_{exec}\)：从当前状态到安全就绪的剩余成本，含日志读取、应用、必要 Undo、结构处理、安装和通知。
- \(\widehat C_{extra\_id}\)：继续核验这个候选预计还需增加的识别成本；已经发生的识别成本在端到端测量中另行计入。
- \(\varepsilon\)：防止除零的小正数。

这是“预计释放的查询量/服务时间”的启发式，不是最优解证明。日志局部性、并发争用和请求抵达时间会影响实际效果。

每次组完成后移除已完成需求，更新少量受影响候选，再选下一组。不能反复把同一个查询或共享根页的收益计入多个已执行组。

### 6.4 恢复成本怎样估计

先采用可测量的简单模型，不引入复杂机器学习：

- 页的候选来源：存活副本接续、顺序日志、随机日志读取；
- 剩余日志条数与字节数；
- 必须写入的页面数；
- 页类型、结构组大小；
- 最近同类任务的执行时间滑动平均。

多个候选共享日志块时按组计算读取成本，不能机械相加。若没有页日志目录，定位日志的扫描成本必须计入，不能只估算最后几条日志的应用时间。

### 6.5 示例：只按热点或只按页类型都会选错

以下是假设值，仅用于解释，非实测。其他路径页和事务条件均已就绪。

| 候选 | 剩余恢复工作 | 可释放请求数 | 预计成本 | 请求数/毫秒 |
|---|---|---:|---:|---:|
| G1 | 热点叶页 `L1`，数据页已就绪 | 80 | 2ms | 40 |
| G2 | 数据页 `D2`，索引已就绪 | 30 | 1ms | 30 |
| G3 | 叶页 `L3`＋数据页 `D3` | 50 | 5ms | 10 |
| G4 | 冷叶页 `L4`，数据页已就绪 | 1 | 0.5ms | 2 |

倾向顺序为 G1、G2、G3、G4。

- “所有索引优先”可能将 G4 放到 G2 之前。
- 只评估单页的即时收益，会认为 G3 中两个页都没有价值，因为单独恢复任何一个都不能完成查询。
- 全部工作仅 8.5ms。如果为了求精确依赖额外阻塞 20ms，优先选择本身已经失去意义。

## 7. 如何控制识别代价

### 7.1 将代价拆成三部分

| 代价 | 例子 | 如何计量 |
|---|---|---|
| 正常运行代价 | 抽样、计数、路径缓存、摘要复制 | 吞吐变化、P99、CPU、内存、网络 |
| 故障后识别代价 | 候选汇总、路径求交、探测、排序 | 增量关键路径墙钟时间、CPU、额外读字节、RPC |
| 优先恢复附加代价 | 小批次、随机 I/O、破坏顺序性、重复扫描 | 额外执行时间、读写放大、总恢复尾延迟 |

识别与必要的 Phase2/日志分析可以并行，但并行不等于免费。分别报告 CPU 总消耗和实际延长恢复关键路径的墙钟时间。

### 7.2 双预算：识别预算与优先回放预算

建议分开设置：

\[
B_{id}=\min(B_{id}^{abs},\rho_{id}\widehat T_{bulk})
\]

\[
B_{prio}=\min(B_{prio}^{abs},\rho_{prio}\widehat T_{bulk})
\]

\(\widehat T_{bulk}\) 是基于此前校准和当前积压估计的批量恢复耗时，不能使用本轮已经发生完的真实耗时“倒推”在线预算。

建议起点：

- 识别关键路径预算：绝对上限 2ms，比例上限 1%。
- 优先恢复预算：绝对上限 20ms，比例上限 5%。
- 探索性恢复最多使用优先预算的 10%。
- 缺少可靠估计时，禁用额外探测，采用首次阻塞和简单有界候选，不先花大量时间测全库。

绝对值只是起点，必须通过预算扫描找交叉点。不可抢占任务可能越过预算；选择前估算是否能放入，运行后报告实际超限，不将预算称为严格的硬实时保证。

### 7.3 何时停止继续查找

满足任意条件就停止增强识别：

1. 墙钟、CPU、探测 I/O、候选容量任一预算耗尽。
2. 已有候选足够填满优先恢复预算。
3. 连续若干轮没有得到更有价值的候选。
4. 剩余批量恢复很短，继续识别的预计成本接近剩余工作。
5. 路径信息严重过期，探测命中率低。
6. 观测不到未完成索引物化任务，实际只有管理接续，应切换到对应问题而非强行做索引 Redo 实验。

对于额外一次探测，可采用保守的“信息价值”判断：预计减少的加权请求等待时间，应大于探测造成的等待和资源争用。两边都用请求毫秒等同一量纲比较；不能把节省的请求数直接减去 CPU 毫秒。

若无法可靠估计信息价值，就使用固定预算，避免把复杂估价本身变成新瓶颈。

### 7.4 不允许优先通道饿死背景恢复

主实验先采用**一次有界优先窗口，随后统一批量恢复**，最符合本次问题。

扩展实验才加入持续动态提升；需要固定的背景资源配额、任务年龄提升和最大等待约束。不能让新热点不断插队，导致总恢复永远不结束。

### 7.5 低故障频率下还要看常态收益

故障期间的识别净收益为正，不代表值得付出长期的高采样开销。单独给出正常运行吞吐损失和内存成本。

可用“每次故障在固定窗口内增加的正确完成请求数”与“正常期每秒损失请求数、假设故障频率”做敏感性分析，但不假定某个真实生产故障频率。

## 8. 如何插到当前恢复流程中

### 8.1 目标时序

**Phase1 分类隔离 → Phase2 副本及有界摘要汇报 → Phase3 固定恢复边界与事务结局 → 一次公共日志分析 → 有界关键组优先回放并发布 → 其余单元批量回放。**

识别尽量在 Phase2/公共分析期间完成；只把无法并行隐藏的新增部分计入额外关键路径时间，但 CPU 和 I/O 仍完整报告。

### 8.2 公共恢复底座

所有用于比较算法的策略必须共享：

1. 恢复编号 `E`、固定日志截止地址 `R` 和可靠的旧写者隔离。
2. 确定的事务状态；不是仅按故障节点 ID 猜测提交结果。
3. 页面或结构组的可信基线、日志覆盖及合法先后关系。
4. `NOT_READY / RECOVERING / READY / ERROR` 状态；只有验证后的 `READY(E,R)` 才能解 IR。
5. 本地缓存、存储缓存及迟到页镜像的版本校验。
6. 回放期间再次故障、失败重试的安全处理；未证明安全时不提前服务。

首轮真实原型可限定：固定表与索引布局、预分配 heap 空间、提交结果已决、恢复期间只接纳点读。先隔离调度问题，后续才加入并发写、未决事务和结构分裂。

不应在当前全局 Undo 仍会撤销健康事务时宣称“所有 B/C 写事务可以继续”。可先在公共准备阶段终结旧事务，或在正确的选择性撤销协议实现后再扩展。

### 8.3 日志只分析一次，别为关键组重新全扫

首轮原型可以从固定基线到 `R` 做一次分析，生成 heap 页日志目录与索引恢复单元目录；所有算法共享该准备成本。

- 前台关键组和后台批量组复用目录。
- 不给每个关键页独立调用一次全扫 WAL 的旧路径。
- 已优先完成的单元，其 `R` 之前工作不能被背景旧日志再次覆盖。
- 未完成单元继续恢复；失败任务保留错误/未就绪状态。
- 需要 Undo 的页面只能在最终补偿完成后发布。

这里比较的是“同一份恢复工作怎样排序”。页日志目录本身属于公共能力；不能把减少全扫的收益全部归因于关键页选择。

未来可复用项目规划的 PAGEIDX 加速目录构建，但它不是本次选择算法的独有优势。

### 8.4 多节点只保留一个恢复任务身份

B/C 可能都发现同一个关键索引页。以 `(E, page_ref/group_ref)` 合并任务与需求，避免两个节点各做一次恢复。

第一版可由存储侧维护单个调度队列，新 GPLM 管理者负责状态发布与唤醒。通知和计数按请求身份去重。

大批次传输与恢复完成发布可以分离。若实现成本有限，采用相同大小的微批次进行所有策略对照，不能只有新策略享有更早发布机制。

## 9. 索引页恢复能力怎样分阶段补齐

### 9.1 阶段 L0：轨迹与成本驱动的调度实验

输入实际采集的：

- B/C 查找路径和等待事件；
- 故障时页类别、可信副本、未就绪集合；
- 单页/结构组恢复成本分布；
- 对外请求到达轨迹。

在离线调度器中比较优先级策略，识别和采样成本使用测得值，并扫描成本估计误差。

索引回放成本若尚不可测，使用明确标注的合成分布和敏感性分析，不能伪装成真实索引 Redo 时间。

L0 用于决定是否值得做内核改造，不能作为端到端数据库加速结论。

### 9.2 阶段 L1：受控静态拓扑的真实原型

公共能力待实现后，先选择：

- 可信的索引与 heap 基线；
- 留有足够空间、故障窗口内不发生 split/merge 的索引区域；
- 真实主键 INSERT/DELETE 产生的待回放索引修改；
- 确定的同 key 顺序和提交结果；
- 固定恢复代，恢复期间只执行点读。

逻辑索引日志可在可信静态布局下映射到稳定叶页/键域，作为调度单元；必须验证完整覆盖和版本，不能把旧计算端页号直接当权威映射。

若使用测试专用的页镜像/物理补丁回放夹具，要明确它验证的是受控页物化调度，不是当前生产日志格式已经支持任意 BLink 页恢复。

对没有内容变化的根/内部页，其接续、加载或页面镜像恢复成本与真正逻辑 Redo 分开报告。

### 9.3 阶段 L2：动态结构和一般故障

扩展到叶分裂、根分裂、同 key 删除再插入不同 RID、未决事务及恢复中再故障。

需要物理/结构修改日志、可验证的结构恢复组，或等价的版本化索引恢复协议。必要依赖扩大后，重新评估候选精度和收益。

不能把一条 `BLINKINSERT` 独立执行成功，当作整条查找路径已经恢复。无法证明局部恢复安全时，扩大恢复范围或退回批量方案。

## 10. 对照策略与消融

### 10.1 主对照

| 编号 | 策略 | 目的 |
|---|---|---|
| B0 | 公共恢复底座＋固定批量顺序，无优先识别 | 主要基线；与新策略使用相同日志目录、微批次及就绪条件 |
| B1 | 索引类型优先：已知入口/内部页、叶页、数据页 | 检验简单结构规则是否已经足够 |
| B2 | 采样访问频率优先，不考虑完整路径 | 检验“热页”与“关键路径”的差异 |
| B3 | 实时阻塞页优先，使用等待量/剩余成本 | 检验无需历史路径的低开销策略 |
| P1 | 阻塞反馈＋采样路径＋小恢复组＋预算 | 推荐主方案 |
| P2 | P1＋预算内补充探测 | 检验增加识别是否值得 |
| C0 | 与 P1/P2 同样采集、识别或探测，但仍按 B0 执行 | 直接测量信息维护开销和预热效应 |

现有未改造版本可作为工程现状观测，不作为省略正确性处理的竞争基线。另设“短任务优先”作为成本模型对照，资源允许时加入。

### 10.2 全信息参考

- 离线保留完整路径、真实恢复成本和请求轨迹，生成 FullInfo 参考调度。
- 在线策略只能使用故障前已采集的信息及已经到达的请求；不得读取未来轨迹或故障后才恢复出的 A 内存状态。
- 使用启发式得到的 FullInfo 结果只是参考，不自动构成理论上界。
- 对很小的任务集可枚举合法顺序求最优值，检查启发式损失；不要把小规模最优结果泛化到全库。

### 10.3 必要消融

- 无路径采样，仅实际阻塞反馈。
- 有采样，无实时反馈，观察热点切换。
- 有单页评分，无小恢复组，观察索引与数据同时缺失。
- 去掉成本估计，观察热点页日志很长的场景。
- 去掉识别预算，观察小积压场景是否反而变慢。
- 去掉置信度/过期处理，观察分裂和缓存失效后的误判。
- 相同排序分别使用 500 页发布和相同微批次发布，分离排序收益与发布粒度收益。
- 按实际布局访问与强制清空 `key2leaf` 分别测试，不能只在无捷径情况下证明根页优先。

## 11. 具体实验设计

### E0：先验证瓶颈是否真实存在

**问题：当前等待究竟来自索引 Redo、管理权恢复、取页，还是全局 barrier/Undo？**

先只观测，不重排：

- 故障时真实待恢复的 heap 页、索引页和结构组数量。
- 待回放 heap/BLink 日志条数与字节数。
- 查询在哪类页面首次阻塞。
- 数据页已就绪但路径尚未就绪的查询数及拖尾时间。
- `WaitReplayCaughtUp()`、日志扫描、应用、Undo、RPC/锁管理各自耗时。

如果故障时没有待回放索引日志，就不能用该场景证明索引 Redo 优先的收益；若主要开销是统一 barrier，先处理公共底座，而不是调选择算法。

### E1：可解释的四类路径微基准

构造固定 A 故障、B/C 存活的四种查询群：

| 场景 | 数据状态 | 索引路径状态 | 验证点 |
|---|---|---|---|
| S1 | 已有可信存活副本 | 热点叶页需要恢复 | 是否优先补索引，缩短索引拖尾 |
| S2 | 数据页需要恢复 | 索引路径已就绪 | 是否避免盲目“所有索引优先” |
| S3 | 数据和索引都需恢复 | 存在 2～3 个必要单元 | 小恢复组是否优于单页贪心 |
| S4 | 大量冷页待恢复 | 少量热点完整路径待补 | 有界优先窗口能否提前释放热点，又不饿死冷页 |

交叉设置页面借用类型：A 持 X、B/C 从 A 持 S/X、管理和持有者均不涉及 A。

额外设置：共享根/内部页受影响、根已就绪但热点叶页受影响、`key2leaf` 高命中与低命中。

记录真实实际达到的锁/副本状态，不能只按预期启动脚本给场景贴标签。索引内容损失与“仅管理者丢失”分别运行，不混合统计。

### E2：识别精度与开销曲线

固定数据和故障轨迹，扫描如下参数；先单因素，再选择关键交互，不做无必要的全笛卡尔积：

| 参数 | 建议取值 |
|---|---|
| 请求路径采样率 | 0、0.1%、1%、5%、100% |
| 每节点路径摘要内存上限 | 1MiB、4MiB、8MiB、16MiB |
| 路径保留时间窗口 | 1s、10s、30s |
| 精排候选上限 K | 128、512、2048 |
| 故障后额外探测预算 | 0、0.5ms、2ms、10ms |
| 识别比例预算 | 0、0.5%、1%、2%、5% 的预计批量恢复时间 |

主要输出：候选覆盖率、真正最后阻塞点命中率、净查询等待收益与识别成本曲线。

100% 采样主要用于测量上限和信息完整性，不默认适合作为在线方案。

### E3：识别预算与优先回放预算的交叉点

扫描优先执行预算：0、1%、5%、10%、20% 的预计批量恢复时间，并记录绝对上限的影响。

至少覆盖：

- 小、中、大实际回放积压；
- 索引日志稀疏与索引修改密集；
- 顺序 I/O 友好与优先组随机分散；
- 热点页恢复成本低与热点页日志特别长。

核心图：横轴识别成本/预算，纵轴固定窗口正确完成请求数或总请求等待。应展示收益从上升到趋平、甚至转负的区间，而不只报一个最优点。

### E4：负载变化与信息过期

- 访问分布：均匀、Zipf 参数 0.8、1.2；另加入 1% 键承载 80% 请求的可控热点。
- 热点变化：故障前后不变、部分迁移、完全迁移。
- 路径变化：稳定布局、提示失效、进入 L2 后加入结构分裂。
- 命中情况：全部命中；另设含 10% 不存在键的点查，检查误报 NOT_FOUND。
- 缓存情况：正常预热、受控冷缓存、`key2leaf` 命中率差异。

验证历史路径能否被实时反馈纠偏，以及 P2 探测在什么条件下值得启用。

### E5：真实负载的端到端效果

#### SmallBank：用作数据恢复和访问等待对照

现有 `test_recovery.sh` 启动三个 `smallbank lazy` 计算节点，参数为 5 线程、0.1 只读比例、0.9 本地事务目标比例。

当前 SmallBank 主要更新既有账户余额，运行期通常不产生主键索引插删。提高写事务比例不能自动制造索引恢复负载。

因此 SmallBank 用于验证：

- 数据页优先恢复；
- 索引路径的管理权接续与访问等待；
- 正常采样成本及多查询事务的延迟。

不能仅凭 SmallBank 结果宣布索引逻辑 Redo 加速。

#### 主键点查＋插删负载：核心索引实验

需要新增或复用 SQL/受控索引测试入口，构造：

1. 故障前：既有主键点查、INSERT/DELETE，以及可控 WAL 物化积压。
2. 故障后：第一阶段只发点读，查询命中和不存在的键都包含。
3. 数据分布和插入间隙控制无分裂窗口，完成 L1；随后才进入 L2。
4. 同 key 删除再插入到不同 RID，作为必须正确处理的扩展测试。

日志积压只能通过可说明的测试钩子、负载或存储限速控制，并对所有策略相同。受控造积压与自然故障分开报告。

真实 crash 前的普通异步执行可能导致各策略初始状态不同。最强配对来自相同的完整恢复夹具；自然故障采用相同工作负载种子，并记录实际积压和持页状态，不能仅因种子相同就声称状态完全一致。

### E6：无收益场景与安全降级

必须包含：

- 几乎没有索引积压，数据和索引本来同时就绪。
- 恢复工作很少，识别比回放更贵。
- 访问均匀，没有少量关键路径。
- 大部分提示只保存在 A，A 故障后信息缺失。
- 成本估计偏差、候选大量过期。
- 重复通知、RPC 超时、损坏日志或无法确认结构状态。

合理结果可以是自动退回 B0/B3，而不是每个场景都强行优先恢复。失败必须保持未就绪或回退安全路径，不能读错。

## 12. 指标定义

### 12.1 主要收益：真实查询更早完成

1. 从实际故障注入起的首次正确点查时间；另记录检测完成后的对应时间。
2. 故障后固定 1s、5s、10s 窗口内的正确完成请求数；窗口可根据试跑恢复尺度预先调整，正式实验中固定。
3. 查询延迟 P50/P95/P99，区分受影响与不受影响路径。
4. 全部存活节点、所有恢复任务真正完成的时间。
5. 相对 B/C 正常可用容量的吞吐损失面积。

不能仅用故障前 A/B/C 三节点吞吐作为恢复目标，因为节点容量本身减少了。报告两节点稳态参考和业务故障前水平，两者含义不同。

开环请求发生器按固定时间表接纳负载，并将排队时间计入延迟，避免“线程阻塞导致请求不再生成”的协调遗漏。闭环结果可作为补充。

超时、失败和测试结束时仍未完成的请求必须报告；不能只对已完成请求计算漂亮的 P99。对固定观测终点 \(T\)，可使用截断等待总量：

\[
L(T)=\sum_{q:a_q\le T}w_q\bigl(\min(c_q,T)-a_q\bigr)
\]

其中 \(a_q\) 是接纳时刻，未完成请求的 \(c_q=+\infty\)。该量与未完成数、成功率一起报告。

### 12.2 专门衡量“数据好了，索引还在拖后腿”

对命中查询，以相同恢复目标下的实际就绪时刻定义：

\[
T_I(q)=\max_{p\in I(q)}T_{ready}(p),\qquad T_D(q)=T_{ready}(d_q)
\]

\[
L_{index\_tail}=\sum_q w_q\max(0,T_I(q)-T_D(q))
\]

同时报告：

\[
T_{path}(q)=\max(T_I(q),T_D(q),T_{txn}(q))
\]

以及真实查询完成时间。否则算法可能通过故意拖慢数据页，虚假降低“索引拖尾”。

历史就绪时间统一截断到本次恢复观测起点，并只比较同一请求群、同一合法路径定义。未命中查询单独统计，不虚构数据页就绪时间。

### 12.3 识别质量

- 请求加权覆盖率：有限预算内识别到多少受影响查询的有效阻塞依赖。
- 最后阻塞点精度：声称“恢复它即可完成路径”的判断有多少真实成立。
- 路径过期率、未知路径比例、探测成功率。
- 优先工作浪费率：在固定窗口内没有帮助任何实际需求的优先任务成本占比。
- 相对 FullInfo 参考的等待差距；若参考为启发式，不把差距称为严格最优性界。

真实标签通过相同布局的离线验证/独立 profiling 获取。正式在线策略不能使用标签；收集完整标签的成本也不能偷偷附加给某个基线而不附加给新策略。

### 12.4 成本与公平性

- 正常期吞吐、P99、采样 CPU、元数据峰值内存、摘要网络量。
- 故障后识别关键路径墙钟、CPU、探测 RPC、额外页读取。
- WAL 实际读取次数和字节数、重复应用量、随机 I/O 和缓存污染。
- 各类恢复单元的排队/执行/发布时间。
- 优先通道预算超限量、背景最大等待、总恢复尾时间。

对多个算法必须固定线程数、恢复并行度、微批次、存储带宽和发布规则。

### 12.5 净收益不要用不同量纲相减

用端到端差值直接计入识别开销，例如：

\[
\Delta L(T)=L_{B0}(T)-L_{policy}(T)
\]

所有时间从同一个故障/恢复观测起点开始。此时新策略花在识别上的停顿已经进入 \(L_{policy}\)，不再重复减一次。

C0 与 B0 的差用于解释识别成本，P1/P2 与 C0 的差用于解释调度及探测效果，最终判断仍以 P1/P2 相对 B0 的净收益为准。

## 14. 实验可复现性与正确性

### 14.1 当前脚本需要调整的地方

- `test_recovery.sh` 当前随机选择故障节点，需增加显式 A/victim 和种子参数；进程匹配参数也要与负载参数同步。
- 脚本中默认故障前等待与故障后关闭间隔是固定值，不能保证负载仍在运行或恢复已经完成。
- 当前会清历史日志而保留数据库。正式实验应恢复同一份完整数据、索引、WAL/Undo 及元信息基线，不能随意删除恢复依赖。
- 程序启动会修改共享配置；不同试验使用隔离的运行目录和配置副本，避免并行互相影响。
- 当前配置中的 `batch_size=400` 是事务批次，不是 Phase4 的 500 页恢复批次。
- 恢复扫描的页面范围、page 0、实际分配页与缓冲池上限要先核验。不能在扩容数据集后漏扫描，再把遗漏当成恢复更快。

### 14.2 数据规模与运行方法

以当前 30 万账户规模和三个本地计算进程做功能试跑，再按实际页容量扩展。大规模必须记录真实树高、索引/数据页数、工作集与缓冲池比例，不只记录行数。

对关键配置至少做 10 次独立重复；可先做 3 次 pilot 估计运行时长和方差，pilot 不混入正式结果。算法顺序随机化，成对使用相同夹具和请求轨迹。

报告中位数、离散程度及按 run 计算的 95% 置信区间。不要把同一次故障中的数十万请求当作数十万次独立故障重复。

参数在独立调参集合上选择；正式测试包含不同种子和热点布局，避免在同一轨迹上挑最优预算再汇报收益。

### 14.3 正确性校验不能沿用静态索引文本检查作为唯一依据

当前 `verify_consistency.py` 主要根据装载时的 `_index.txt` 检查 heap 字段，并不验证恢复后实际 BLink 的完整键/RID 集合。

新增校验至少包括：

1. 固定恢复截面下的预期提交键集合、值和 RID；提交确认语义必须先明确。
2. 实际 BLink 与 heap 的双向一致性，包含 bitmap、valid、实际 key。
3. 已提交插入不丢失、已提交删除不复活、未提交修改不对读请求可见。
4. 恢复期间的 NOT_FOUND 不得来自未就绪索引。
5. 同 key 重插不同 RID、重复任务、迟到旧页、超时和再次故障。
6. 发布后的页面不能被后续旧日志或旧镜像覆盖。

协议尚未支持的故障应保持错误/未就绪，而不是算一次成功恢复。失败样本单独报告，不能从性能汇总中悄悄删除。

## 15. 推荐的最小实验推进顺序

### 第一步：仅观测，回答“有没有值得优化的拖尾”

实现阻塞原因、真实路径和页就绪时间观测。运行 E0，输出索引拖尾分布、日志积压与阶段耗时。

若没有真实索引积压，先构造可控插删负载；若全部时间耗在全局 barrier，先解决可调度底座。

### 第二步：离线比较 B0、B1、B3、P1

使用相同故障夹具和请求轨迹，先确认小恢复组与少量采样是否具有稳定潜力，并找到大致识别预算范围。

此阶段不需要直接完成任意 BLink 页恢复，不夸大为真实数据库加速。

### 第三步：L1 公共底座＋真实优先窗口

在静态拓扑、提交结果已决、恢复期间只读的条件下，提供正确的索引/heap 恢复单元。

保持主对照底座一致，接入一次有界优先窗口，执行 E1～E3。

### 第四步：只在有净收益后加入 P2 和 L2

探测、成本模型复杂化、持续动态提升、结构分裂和读写并发分别增加，逐项消融，不一次把所有机制叠加后才比较。

### 第一轮建议配置

| 项目 | 建议起点 |
|---|---|
| 故障 | 固定 A，B/C 存活；另做自然随机故障验证 |
| 采样 | 每请求 1%，每节点 8MiB 上限，10s 时间窗 |
| 精排 | Top-512 候选，有界小组 |
| 额外探测 | 默认关闭；单独测试上限 2ms 的增强项 |
| 识别预算 | `min(2ms, 预计批量恢复时间的1%)` |
| 优先预算 | `min(20ms, 预计批量恢复时间的5%)`，一次窗口 |
| 发布 | 所有主策略统一使用小批次；起点 16 个独立页，结构组不可强行拆开 |
| 主要策略 | B0、B1、B3、P1、C0；随后增加 B2、P2 |
| 核心负载 | 可控索引插删积压＋故障后点读，SmallBank 作对照 |

这些上限需要结合实际恢复尺度校准。16 页批次不意味着任何 16 页都能无依赖并行。

## 16. 结果应该怎样呈现与判断

建议至少生成六类图：

1. **恢复时间轴**：公共准备、识别、优先回放、背景回放、首个/批量正确查询。
2. **索引拖尾 CDF**：数据就绪后还等索引多久，配合整体路径就绪时间。
3. **预算—净收益曲线**：展示探测或采样成本的收益拐点。
4. **成本分解**：采样、候选维护、探测、WAL 读取、应用、Undo、发布。
5. **热点与布局变化**：不同缓存命中、热点迁移、索引/数据同时缺失时的效果。
6. **正常开销与恢复尾延迟**：避免仅报告首批查询的改善。

正式结果表至少包含：策略、样本数、实际索引/数据积压、识别开销、额外 I/O、固定窗口正确完成量、P99、索引拖尾、总恢复时间、正常吞吐损失、正确性失败数。

可预先采用以下工程目标作为约束，而非性能承诺：正确性错误为零；常态吞吐损失尽量不超过 2%；总恢复时间恶化尽量不超过 10%。若目标不满足，应报告并调整范围，而不是仅选有利场景。

最终应回答四个问题：

1. 关键页主要能由真实阻塞发现，还是必须依赖历史路径？
2. 多少采样和探测已经足够，继续识别从哪里开始得不偿失？
3. 收益来自真正提前补齐查询路径，还是来自更小批次、缓存预热、少扫 WAL？
4. 在没有明显热点、积压很小或提示失效时，策略能否及时停止额外工作？

### 18.2 核实的源码事实及本轮差异

1. **追平在定向恢复之前，仍然保留。** `AnalyzeRecoveryPages()` 仍先 `WaitReplayCaughtUp()` 再暂停 replay，没有删除等待，也没有把 BLink 逻辑键日志按计算端页号强行回放。夹具显示：进入后续定向分析时，heap/BLink 待物化日志均已归零；`RedoForPages()` 没有真正应用页面工作。因此重排该 RPC 不能证明索引物化提前。
2. **新增的 E0 缺陷证据：v2 填充边界。** 写侧尾地址是完整 32KiB 块末尾，旧回放进度停在有效记录末尾；只有一条提交记录且 `persist_batch=1` 时也会超时。新增 `LogStreamReader::NextReplayAddr()`，仅在块经过 CRC 校验且有效载荷完整消费后计入填充。坏块/短记录不能借此追平。读侧跨段条件与写侧整块滚动条件对齐。
3. **暂停必须覆盖应用。** 原 `replayFunV2()`/legacy `replayFun()` 只在循环开头短暂持暂停锁；本轮让锁覆盖实际回放，空闲睡眠前释放，另将退出标志改为原子量。WAL 地址保持 64 位，已应用位置统一为最后字节。后台 10ms 轮询周期未改小。
4. **仍没有索引物理页日志目录。** `RedoForPages()` 仍只解析 heap UPDATE/INSERT/DELETE，仍以 `std::map` 固定顺序执行。BLink/FSM 页不再被误读为 `RmPageHdr` 或送入 heap 定向回放。P1 没有接入此处，PAGEIDX/索引恢复单元目录仍待实现。
5. **失败路径加固，不是完整 READY 协议。** 追平失败、已知目标 LSN 未达到、扫描/读页失败、RPC 失败、响应身份/条数/状态不合法时保持隔离；不能再通过错误状态或 RPC 失败直接解 IR。定向结果区分“完整扫描但无待回放记录”和“执行失败”。Undo 前置条件或 fallback WAL 读取失败返回负值，不登记 Undo 完成。
6. **Undo 没有缩减。** 仍调用 `UndoAllActiveTxns()`，涉及全部活跃事务；未实现只撤销 A 的可靠事务协议。`page_data` 在 Undo 后重新读取，返回 LSN 与该镜像一致。现有日志文本中的 `Undo transactions` 实际打印的是操作数，不能直接解释为事务数。
7. **副本报告只加固了明显的非法情况。** `ReportPageStatus()` 不再因无有效副本/无 S、X 持有模式的报告解锁；这仍不能验证副本版本、granting 中间状态、迟到镜像或事务可见性。管理者不是最新持有者，此处不能作为副本已验证的证明。
8. **发布底座尚未改造。** 线上仍是每批 500 页的原 RPC 发布路径，没有生产微批次调度队列。五种策略只在 L0 中共享依赖、一个恢复工作者和同一发布粒度。
9. **内容校验暴露的小问题。** 存储侧 `S_BLinkIndexHandle::search()` 对合法未命中原先 `assert(exist)`；删除该断言，使真实已删除键可被校验。后台 DELETE 维护 heap 记录数，使其与 bitmap 相符。计算端 `key2leaf` 分支释放临时叶句柄，避免高频观测路径泄漏。
10. **参考文档不是当前协议承诺。** `RECOVERY_FLOW_DETAIL.md` 仍描述旧版单页回放、仅故障节点 Undo、失败解 IR、全局 epoch abort；当前源码已有批量回放、独立 Undo 区和 tainted 逻辑，本轮又加固错误返回。`LOG_SYSTEM_DESIGN.md` 的 PAGEIDX/checkpoint、日志目录、并行恢复仍不能假定存在。`UNDO_DESIGN.md` 的全活跃事务语义与当前实现相符，但不构成健康写事务可持续执行的证明。

事件约定：

- `lookup_begin`/`path_page`/`key2leaf`/`lookup_end` 包含实际路径、采样标志、键和目标 RID；NOT_FOUND 的目标页为 -1。路径通过原查找顺路采集，无额外探树 I/O。
- `generation` **只是本进程已观察到的 split 代数**，不是跨节点权威拓扑版本。远端结构变化、重建/迟到缓存的失效协议尚未完成。
- 连续同原因的 1ms 轮询只产生一次 `block`；`unblock` 记录耗时和是否成功解除。重新访问、原因迁移是不同事件，不能把原始事件总数直接作为跨请求需求量。
- 生产 `RequestScope` 的范围是 lazy 同步 `TxExe`，不覆盖完整 SQL 接纳、异步/协程上下文、事务重试/提交全链路；不能由它报告生产“正确提交请求数”。
- `page_access` 是访问完成，`ir_released` 是管理锁释放，`storage_post_undo` 是存储处理完成；**都不是分布式 `READY(E,R)` 证书**。只有测试夹具的 `fixture_ready` 有本夹具限定的静态内容校验依据。
- `backlog_heap/index/control` 的 `a/b/c` 分别为待回放条数/记录字节/扫描完整标志；`backlog_bounds` 的 `a/b/c` 为起始/排他尾地址/实际读取字节。扫描不完整时是下界，不得当零积压。这里测的是存储故障通知接收截面，不是已经校准的物理 crash 截面。
- 阶段事件的 `a/b/c` 为墙钟微秒/当前线程 CPU 微秒/结果。嵌套阶段不能简单相加当总恢复时间；后台线程总 CPU、观测输出线程 CPU 和正常吞吐开销尚未完整测量。
- `buffer_capacity_bytes` 是整个缓冲配置的上界，不是实测 RSS；本轮 `trace_summary` 的零丢失仅说明这些小夹具完整。

L0 的任务状态是真值模型，选择器只能看到已经到达的请求的当前阻塞点及 B/C 历史样本；未知/过期依赖不用于“恢复该组即可完成”的强评分。恢复闭包和完成判定不由采样提示决定。任务/报告去重在单个 L0 协调器中完成，尚非真实多节点 RPC 去重实现。

### 19.2 新增/完善的工程能力

**真实取页与安全失败：**

- 在 `MetaManager`、`ComputeNode`、`ComputeServer` 中增加显式 `InProcessTag` 依赖注入构造入口。夹具不读取共享配置、不启动生产构造器的 detached 线程、不创建 Raft 文件；原有构造入口保留。
- 真实 lazy S/X 入口、真实 LPLM 和 GPLM，通过本进程拥有的 `127.0.0.1:0` 临时端口验证远程调用；本地管理者分支与本地缓存分支均覆盖。服务由局部对象停止并 join，不使用按名称匹配的 kill。
- `GetPage`/`GetPageWithLsn` 的 RPC 失败、短页、heap LSN 不满足要求时抛出 `recovery::PageUnavailable`，不再返回零填充页。只有 GPLM 明确授权存储来源时才允许 lazy 的存储获取；丢失副本或被中断的推页不能默默回退到未验证存储。
- 取页在保留本地锁后失败，保留本地 quarantine；后续请求明确报错，普通重试和观测开关不能解除隔离。**这会牺牲可用性以避免错误服务，不是已经实现失败后的自动安全重试。** 生产上层如何清理整个事务、重新建立全局持有关系仍未完整实现，不能作为一般写事务可用性承诺。
- 实测发现 `LRLocalPageLock::getLock()` 原返回 `int`，把高位的 64 位排他锁截断为 0；改回 `lock_t`。X 释放前断言与真实持锁状态一致，也避免错误的 S/X 分类。
- IR 无锁检查使用原子标记。锁表和有效性表可显式指定测试容量，并正确释放资源；测试只使用 32 页，生产默认 `ComputeNodeBufferPageSize` 不变。

**观测与计量：**

- `core/recovery/observation.h` 格式升级为 schema 2，增加逻辑请求、尝试号、接纳时间与取消/截止时间；`ContextScope` 支持显式跨线程传递上下文。测试中同键/同页的独立请求不再冒充同一个逻辑请求。
- 生命周期受限的上下文/取消指针必须由调用者保持有效，异步任务须在所属请求结束前完成。当前并没有自动把整个 SQL/协程/事务提交链路改造成新的接纳系统。
- 原缓冲 `vector.erase(begin, ...)` 改为固定容量环形队列；线程退出后槽可复用，不会累计创建超过 32 个线程就永久丢追踪。保留容量溢出计数，分析端拒绝丢事件或未完整关闭的轨迹。
- 记录缓冲配置上界、实际分配、峰值事件量、已输出事件量以及输出 CPU/墙钟。子进程记录完整 CPU、墙钟和文件系统块 I/O；夹具记录 `getrusage` 峰值 RSS。RSS 是进程高水位，包含运行时等成本，不能用开关两次高水位直接当采样内存增量。

### 21.3 P1F：归因支持的最小改进与等价性

依据上述已证实瓶颈实现命名改进 **P1F**（保留原 P1 与全部基线，不替换任何历史算法）：

1. **预算不可行早退**：当剩余优先预算小于最廉未决任务成本时，任何候选组都不可能放入，直接返回空决策。与全量扫描的返回结果完全相同，只是不再为空决策付费。
2. **按请求身份缓存 hint 解析**：请求的 key 与 generation 在一次运行内不变，逐决策重复的 `online_key` 解析与摘要查找缓存为每身份一次；成员测试用路径集合。缓存规模以等待请求数为上界（本轮 ≤200）。
3. **倒排索引评分**：`gain = 0.1×blocked + 0.9×full` 与参考实现的 `Σ[1.0 if 全缺失⊆组 elif 阻塞∈组: 0.1]` 代数等价；从“每候选×每可见请求”降为“每候选×组内页的反碰集”。

三项都是纯重复扫描/维护开销削减：不偷看真值、不改结果分母、不放宽就绪条件、不扩大批次。已知语义差异：截止期压力下原 P1 可能在单候选评分中途截断产生部分分，P1F 只在候选之间截断；冻结时钟下两者选组完全一致（见下）。

**当前 GO/验收边界：** 允许立即实现真实负载和普通恢复基线；真实优先恢复仍须在正确性底座验收后接入。普通恢复可使用全局屏障，不以提前服务作为第一阶段要求；后续算法是否有收益由真实实验决定。

### 22.4 真实负载契约：确实执行增删改查

**执行链：** 负载驱动 → 客户端协议 → 计算端 SQL/事务执行 → 真正 BLink 与 heap/FSM → 正常 WAL 写入/提交确认 → 存储 replay。首选真实 SQL；如 SQL 性能或功能需分阶段补齐，可以先用等价 C++ 事务驱动诊断，但必须经过同一持久化链路、明确不是 SQL 端到端结果，不能用直接写页替代主验收。

- 数据模型：一张有唯一整数主键的表，固定长度非键值、应用版本号/校验字段。具体 SQL 类型/长度以解析器和存储格式实际支持为准，先做 schema 能力测试，输出实际序列化记录长度；不沿用上一轮口头估算的记录大小。
- INSERT：新键；重复键应有确定的拒绝结果，不当 UPSERT。DELETE：已有键与不存在键；UPDATE：已有键的非键值与版本、更新不存在键；SELECT：命中和合法 NOT_FOUND。串行契约测试涵盖这些分支后，才做并发混合负载。
- 必测序列：INSERT→SELECT、UPDATE→SELECT、DELETE→SELECT 未命中、DELETE→再 INSERT 同键新值、重插后 RID 改变时的正确映射、显式提交/回滚、执行中取消/断连。大表中 RID 是否复用以实际结果为准；专门用例确保“同键不同 RID”分支确实覆盖。
- 初始混合比例拟定 SELECT/INSERT/UPDATE/DELETE＝40/20/20/20，四类均非零；这是实现起点不是实测最优参数。先分键所有权减少意外冲突，再单独加入 B/C 共享热键和跨节点读写；预先选定均匀、固定热点、热点切换三个负载，不根据算法结果择优。
- 保持记录数受控：独立维护当前存活键、新键区、已删除键与不存在键区；DELETE/INSERT 平衡，防止树在长跑中无限膨胀或数据集被删空。主性能请求优先单键事务；另设小规模多语句事务测试 Undo，不将多语句未验收行为默认为正确。
- 开环到达可配置，排队时间计入延迟；驱动达不到设定速率时报告实际接纳、队列和背压，不能用阻塞客户端悄悄缩小分母。无故障阶段先量容量，再冻结试验请求率和窗口，不继承 L0 的 2000us 窗口。
- 负载台账：外部驱动持久记录 run_id、request_id、节点、事务标识、操作/键/版本、计划/接纳/回复时刻、原始返回值、提交证据/错误。明确区分已确认提交、已确认中止、结果未知、仍执行；台账供独立校验，禁止提供给在线优先选择器作为未来需求或完整路径真值。
- 响应丢失或故障时的 in-flight 事务不可直接判“未提交”：通过可信事务结束记录核定固定截面内结局；无法核定则整次正确性验收未通过。首版不承诺 exactly-once 自动重试，需请求去重或先查明结局。
- 主键查询必须验证实际执行计划/测试计数使用 BLink，而非 SQL 优化器退回全扫描。`key2leaf` 保持正常语义，命中/回退分别报告，不为了突出根页瓶颈偷偷清缓存。

### 22.5 规模门槛：真实生长的 4～5 层 BLink

**层数定义：** 根为第 1 层，叶为最后一层；索引文件头页、heap 页、同层右链跳转不计入高度。`key2leaf` 绕过的节点仍存在于树中，不能用单次访问页数充当树高。

1. **自然布局为主验收。** 保持默认 4096B 页面、真实 key/RID 布局和实际分裂规则，经真实 INSERT 生长。R1 主规模至少实测 4 层，5 层作为更大规模档；两档分别记录，4 层通过不得声称 5 层完成。不得手工拼一棵稀疏高树冒充大数据，也不得通过修改全局 `PAGE_SIZE`/fanout 偷换规模。
2. **先测容量再定行数。** 两端构造器根据 `sizeof(BLNodeHdr)`、`sizeof(itemkey_t)`、`sizeof(Rid)` 计算 `order`；实际占用、装载键序、split/删除决定高度，不能直接写“百万行必为 4 层”。实现只读结构检查器，输出 ABI 大小、物理容量、split 阈值、实际记录数和树高。
3. **逐级装载。** 小规模仅作冒烟，然后按预定增长倍率分批真实 INSERT，每个检查点排空事务并验证结构。到达目标高度且内容正确后停止；加载时间、峰值 RSS、磁盘/WAL 增量、页号范围和缓存容量一起报告。先计算资源与时间上限，达到上限未到高度则报告 R1 规模未通过，不无限跑满磁盘或交换内存。
4. **结构验收。** 在无并发结构修改的稳定视图，从根逐层遍历并验证：全部叶深度一致、内部分隔键和孩子范围、叶键序、兄弟链与 high-key、无环/重复可达页/丢失键、header/root 合法。记录每层页数、占用率分布、索引/heap/FSM 页数与字节、工作集/缓冲池比例及实际命中率。检查器不得自动修树或装载时重建来掩盖错误。
5. **两端分别验证。** 计算端实际树与存储端逻辑 replay 后的树都统计高度和内容。它们可能有不同物理页号/布局，不能要求旧叶页号逐一相等；正式规模档要确认被测查询树和待恢复索引都达到声明高度，任一未达单独报告。恢复后仍检查结构有效和逻辑内容一致，而非强求物理树形不变。
6. **小 fanout 只可为辅助测试。** 若自然 5 层超资源预算，先交付实测 4 层及 5 层所缺资源，不自动改成缩 fanout。缩 fanout 方案须另行明确确认并标为“受控多层结构测试，非自然大规模”；当前 `order` 同时决定 RID 数组偏移，不能只改一个数字；若设计独立 split 阈值，必须与物理布局分离，计算/存储/重放一致，并保存到快照兼容元数据中。

### 22.6 R0/R1 验收：先跑通、再放大

- 重建当前源码的计算、存储、远程锁服务和相关测试；明确 Debug/Release、优化参数、版本/指纹，历史二进制结果不得代替本次重建。功能验证保留必要断言，性能构建不能以 NDEBUG 令未实现算子“成功返回”。
- 为每次运行创建独占目录，复制或显式传入独立配置；审计 DB、WAL、Undo、Raft、元数据及日志的真实路径。服务构造器的相对路径、端口、线程和配置改写必须纳入隔离，而非只改变 stdout 路径。
- 先单连接验证四类 CRUD、显式提交/回滚、错误响应与机器可读值；再 A/B/C 真实进程无故障混合负载，验证跨节点可见性。运行中即时抽查，静止截面全量流式校验；记录所有失败/未知，不能只展示成功请求。
- 普通 SQL 操作产生的实际 heap INSERT/UPDATE/DELETE、BLink INSERT/DELETE、FSM/分配/提交/Undo 记录分别计数；确认链路确实落到共享存储。装载、业务写和 SELECT 引起的锁元数据日志分开，不用写比例推断索引积压。
- **提交保证按故障模型定义。** 第一目标是仅计算进程故障、存储进程和宿主机存活；服务返回成功必须对应可核查的事务结束与 WAL 接收/持久边界。`write/pwrite` 与 `fdatasync` 分别说明，不能把此结果外推到存储崩溃/掉电耐久性。
- R1 通过必须同时具备：CRUD 正确性、真实日志闭环、无故障运行结束、至少自然 4 层结构/内容证据、可重复命令和完整 manifest。达不到时定位并修复，不用新的合成模型替代。

### 22.7 R2：先验证不带优先算法的普通故障恢复

**故障模型：** 新建隔离环境中，A/B/C 运行真实 CRUD，人工 SIGKILL 本次启动且核验身份的 A；存储、锁/元数据服务及 B/C 存活。进程崩溃是实际事件，不用 `SetReady(false)` 替代；通知入口调用本身不等于故障注入。物理断电、存储进程故障、多节点同时故障另列扩展。

**起始基线和两级故障：**

- R2a：先做已决事务的可定位故障点（例如持久接收确认后、实际 replay 未完成），验证基本 replay/管理接续/重新服务。这是受控窗口，不宣称随机时刻容错。
- R2b：在真实混合负载执行时人工故障，涵盖未提交 INSERT/UPDATE/DELETE、回复丢失、健康节点 in-flight 事务；若有故障点钩子，报告确切位置，不用“睡 N 秒后 kill”宣称命中某日志或 split 阶段。
- 建树时 split 是真实执行；首个可定位窗口可避免进行中的 split，但要明确限制。普通恢复一般性结论还需专门覆盖叶/内部/根 split 期间故障，或证明能安全保持隔离并报告不支持。当前 merge 未实现，删除正确性不要求凭空增加 merge；页回收、缩根另行设计。

**恢复时序和边界：**

1. 驱动保存注入指令、实际终止时刻、故障检测/通知、服务端恢复代；登记本次 PID 的启动时间/可执行路径，禁止只凭进程名 kill。
2. 第一版允许故障检测后全局暂停新写、阻止旧事务继续提交，按统一恢复代排空/隔离健康节点旧事务及日志，冻结 WAL 边界。仅停客户端发新请求不够，还要处理在途日志、迟到提交和旧 RPC。不能让 `UndoAllActiveTxns()` 一边撤销 B/C，一边允许 B/C 无约束提交。
3. 第一阶段请求可以排队至全量恢复/校验完成再放行；普通基线不要求提前 READY。保留必要 replay 追平、暂停和 Undo，不为速度删除等待。全活跃 Undo 可以在明确定义的全局暂停模型内保留，不强制先实现一般选择性 Undo 协议，但失败/跳过不能误标成功。
4. 运行完整 Redo/Undo、缓存/副本安装、管理接续和错误检查；完成必须有实际任务/日志/事务终局依据，而不是固定 sleep。IR 集合为空也不能跳过应做的事务终结；RPC 错误、损坏日志、缺失前镜像保持隔离，不能重建空页放行。
5. 在稳定截面做全量校验，通过后 B/C 恢复 SELECT，再恢复正常 CRUD，验证可持续写入和再次查询，而不是只验证存储侧磁盘内容。A 重加入首版可不做；未清代际/缓存状态前不自动重启旧写者。

**独立正确性判据：**

- 外部操作台账＋可信事务结局/WAL 截面确定预期键、值和版本；收到已确认成功的插入/更新不能丢，已提交删除不能复活，未提交变化不能可见。未确认响应不能自动作失败；结局未知未解析则不出性能通过结论。
- 实际 BLink 全叶 key→RID 与 heap bitmap/valid/key/value 双向一致，检测孤儿记录、悬空 RID、重复键、错值及记录计数；检查 FSM/页分配元数据可继续使用。不能只对照装载时 `_index.txt` 或静态基线文本。
- 索引路径不可用时只能等待/明确报错，不得返回伪 NOT_FOUND；检查存活节点缓存和迟到页是否覆盖已恢复内容。全量检查按流式/分区进行并记录自身时间，不能让验证器只返回采样 PASS 冒充全量一致。
- 无故障基线、R2a、R2b 均有独立结果；恢复后验证同一树高档的结构，不把不同实验中的请求当独立故障样本。一次通过只是功能证据，后续重复注入须从新的独立环境或经验证的同一持久基线开始。

**真实积压必须取证：** 注入/检测/固定截面分别记录持久 WAL 尾、已应用位置和待回放 heap/BLink/控制日志条数与字节。若自然后台太快，可使用显式测试钩子或限速，在持久接收后、物化前造真实积压；各策略共用同钩子/阈值，不改成合成耗时。索引积压为零的运行仍报告，但不能用于证明提前索引物化收益。

### 22.8 R3：公共恢复底座与可插拔策略接口（R2 后实施）

**接口只决定合法工作的优先顺序，不拥有正确性权限。** 必须把“识别/调度”和“事务、日志、执行、发布”分开；实现时先提交接口契约和测试，再逐个接算法。以下命名是拟议 C++ 契约，不是已有类或 CLI 参数。

| 公共组件/接口 | 拟议输入与输出 | 必须遵守的边界 |
|---|---|---|
| `RecoveryContext` | recovery_id/epoch、固定 WAL 截面、元数据/拓扑版本、事务结局视图、预算与资源配置 | 由公共底座生成；算法不能延后截面、修改事务结局或改变副本可信性 |
| `RecoveryTaskCatalog` | 唯一 TaskId、heap 页或稳定索引键域/结构组、合法前驱、日志范围/字节、可执行状态、共享成本估计 | 物化前一次公共分析生成；索引任务不以故障前计算端叶页号作为权威身份；同 key/依赖顺序不得打乱 |
| `DemandSnapshot` | 已接纳请求当前 blocker、去重计数、取消/迁移、允许使用的 B/C 有界摘要及版本 | 不含未来请求、模拟真值完整路径、A 丢失内存；缺少信息必须为 unknown，不能猜最后阻塞点 |

**先实现接口版 B0：** 与 R2 未启用接口的原普通恢复作正确性与公共改造开销对照。以后 B1/B3/P1 都对这个公共 B0 比较；目录构建、减少 WAL 重扫或公共发布改进的收益，不能算给某个优先算法。

**真实索引入口限制：** 当前 `AnalyzeRecoveryPages()` 先等待 replay 追平；`RedoForPages()` 主要是 heap 日志并按 `std::map` 执行。接口必须位于确有待物化工作的阶段。不得删除等待制造竞态，不得只排 RPC 页数组就命名“索引优先 Redo”；可以在建立固定截面、停止旧应用、一次日志分析和可信基线后增加显式物化队列，而不是在后置检查中装饰排序。

**初版优先范围：** 使用真实装载形成的多层静态布局，故障窗口内提交结果已决、无 split/merge，恢复期间不接纳会改变恢复基线的新写。同布局下把逻辑索引日志映射到经核验的稳定键域/叶范围，确保覆盖、同 key 顺序、跨 heap/索引事务依赖与日志不重复覆盖。共享祖先不应强制把全树后代合成一个巨组。若当前逻辑日志与页镜像不能证明局部安全，扩大原子任务或回退全量；此时“普通恢复通过”不能写成“优先索引物化通过”。

业务只读阶段若 SELECT 仍会写锁元数据，必须先提供不破坏固定截面的读语义，或继续阻塞这类请求；不能仅因 SQL 是 SELECT 就假设恢复期间无写。动态 split 故障可在 R2 验证全量恢复，而首版 R3/R4 不支持局部提前发布，两者范围分开。

### 22.10 真实对照、指标与 go/no-go

- **公平输入**：保存实际数据库/索引/元数据、WAL/Undo、配置与版本组成的完整一致持久基线，记录 manifest 和内容指纹；恢复为每次运行独立副本，不覆盖源。live 进程间缓存/锁状态不可凭文件复制假定相同，需从基线按固定流程重建并核验。

### 24.5 新窗口必须先处理的阻断与未闭合契约

以下前两项是交接时确认的**源码级编译阻断，尚非编译器实跑结果**；其余为确认存在的代码缺口或待验证风险，不把推断写成 `004` 已证明的根因。行号仅为交接时定位，后续以符号为准。

1. **返回值类型错误**：`logreplay.h` 约 365/370～372 行，内部 `InvalidateAllReplayPagesLocked` 声明为 `void`，`logreplay.cc` 实现也为 `void`，公共 `bool InvalidateAllReplayPages()` 却直接返回该 void 表达式。需先统一真实接口与错误语义，不能只为编译把错误吞掉。
2. **未定义变量**：`server.h` 约 2252 行，Phase1 仍用 `surviving[p % surviving_count]`，本窗口删除了局部 `surviving_count` 定义。修复后仍须检查空 survivor、路由一致性与代际。
3. **cache 修复不完整**：现有草稿仍会丢脏页；实际 `write_page` 异常没有统一置 poison；`PauseReplay` 忽略 flush 的 false，catch 仅记日志；`WaitReplayCaughtUp` 只在入口查 poison，成功返回前不复查。若错误发生在等待中，仍存在错误追平路径。缓存失效放在部分正常出口，失败返回/异常会跳过，调用结果也未检查；哈希键不是完整文件身份/代际。按 2048 条日志 flush 的短尾问题也**没有修复**，须审查空闲、暂停、`ValidationCut`、定向 Redo/Undo 及所有直写路径。不能声称丢页会自动由幂等 replay 补回。
4. **alive 过滤不是全局恢复协议**：仅跳过存活节点 Undo，不能证明其未决事务正确终结，也不能替代关闭旧写者、固定 WAL 尾和新请求门控。UndoArea 使用日志节点身份，但 fallback 用 `tx >> 48` 猜节点；两者契约不一致。应优先明确统一恢复代下的全局暂停/旧事务终结，而不是直接接受本窗口选择性 Undo 草稿。不能未经论证地把存活节点事务交给“以后自己结束”。
5. **Undo 可能虚报成功**：`UndoArea::UndoAllActiveTxns` 坏链仍 `break`、坏记录仍 `continue`，随后写 `UNDONE`/回收链；调用方回调丢弃 `ApplyUndoWalRecord` 的 false，fallback 也只是少计数。false 同时包括幂等无操作和缺前镜像/文件不可用等失败，必须区分，失败不可发完成证书；还须避免部分 Undo 后再次 fallback 重做造成错误。
6. **barrier 尚无 epoch/名单验证**：当前仅以 failed node 分桶，存活名单只取数量，没有保存和验证 reporter 身份集合，RPC 也没 recovery epoch；旧代、名单外报告仍不能安全隔离。保留早到通知解决的是一种时序风险，不足以证明 `004` 就由此导致；超时改失败后还要保证所有节点保持隔离、不被其他路径提前发布。
7. **副本新鲜度与页身份仍不充分**：`ReportPageStatus` 仍以持锁、正 LSN、LSN 不落后为依据设置 newest 并清 IR，没有提交/补偿完成证明；GPLM 重置为 0 后更不能证明副本权威。发送端仅按表 ID 范围把派生表 LSN 置 0，未完整核验实际缓存页类型/版本。普通取页使用 `ComputePagePath`，恢复分析却直接打开请求表名；须沿真实路径检查是否混用计算端物理 BLink 与存储逻辑 replay 树。派生页返回 `status=0` 不能自动解释为同一物理页已恢复。
8. **admission 尚非原子屏障**：`recovery_in_progress_` 仍在 Phase2 扫描之后才置位；请求先读 bool，再在另一把 mutex 下登记 active；没有与恢复开始共用门控临界区，也没有健康节点在途事务/迟到 WAL 的完整屏障。单独拒绝新请求不代表全局截面固定。
9. **事务终局异常处理仍需重做契约测试**：虽然增加了 `TX_COMMIT` 保护和回滚后 UNKNOWN 复查，但解析、accepted 发布、`TxBegin` 等在主 try 外，catch 内 UNKNOWN 发布仍可能再抛；发布失败、重复发布、socket 收尾及部分提交异常不能一律当中止。已有“异常时事务必然未提交”等旧注释过强。数据一致性断言保留，错值/stale RID 不是可以反复重试消化的正常恢复事件。
10. **驱动和诊断仍有漏口**：`fault_contract` 的探测仍捕获广泛 `RuntimeError` 重试，可能吞掉 UNKNOWN、错值、格式错误；没有配套处理新 admission 拒绝的完整台账契约。IR X 等待补的是计数，不覆盖外层 RPC 重试的真实墙钟；计算端前置结果校验后的失败日志不可达问题尚未修复。不要靠增加超时继续盲跑。
